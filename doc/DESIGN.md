## 一、项目定位：这是什么东西

### 一句话

**一个以玩家为中心的交互媒介。** 世界模拟是它的手段，不是它的目的。

游戏首先是一种**媒介** —— 媒介的意义在于它对玩家做了什么，而不是它自身多么精密。
「演化」与「模拟」是为体验服务的工具：**什么时候该细、什么时候该放**
取决于"这样玩家会不会更投入"，而不是"这样世界会不会更自洽"。

> ⚠️ **不要写成"可持续演化的世界模拟器"。** 那个说法把手段当成了目的，
> 是"自成一派的孤立运行的世界"的思路 —— **用户 2026-09-13 明确否掉了它**
> （他上过媒介相关课程，认为媒介思想很重要）。

### ⭐ 角色扮演是根基，不是可选风格

用户 2026-09-13 强调（原话大意）：

> **角色扮演还是很重要的，不能是环世界或者都市天际线这种纯模拟经营。**
> 毕竟**玩家坐在电脑前输入命令这个动作本身就是沉浸化的** ——
> 他和游戏世界之间的联系是非常紧密的。

这条排除了一整类设计（上帝视角的模拟经营），并定下了玩家的位置：

| 原则 | 含义 |
| --- | --- |
| 玩家**在世界之内**，不在世界之上 | 他有一个身份、一个位置，而不是一个抽象的"操作者" |
| **输入这个动作本身**是体验的一部分 | 所以输入的权重、节奏、措辞都影响沉浸 —— 不能把它降格成参数调整 |
| 模拟的精度**服务于代入感** | 不是"为了让世界更真"，而是"为了让玩家更在场" |

### ⭐⭐ 提示词 = 作者控制 AI 的代码

**这是整个项目最重要的一句话**（用户 2026-09-13：*「这句话我非常非常喜欢，可以放到很高的层面上」*）。

> **提示词不是"给 AI 的建议"，而是作者用来操纵世界的编程语言。**
> 作者写提示词，就是在写这个世界的规则 —— 只不过跑它的不是 CPU，是语言模型。

它直接推出了整个架构的价值观（见下节「控制权的归属」），也解释了为什么：
- 卡必须是**声明式**的（作者不写 JavaScript，但写精确的自然语言）
- 引擎**不预设任何规则**（那等于替作者写代码）
- 提示词的**措辞质量**就是卡的质量 —— 这是"让强作者脱颖而出"的着力点

### 三个产品级目标

| 目标 | 含义 | 设计含义 |
| --- | --- | --- |
| **① 不写死规则** | 规则不该由引擎写死 —— 但**不是**为了"让 AI 自由发挥"，而是**控制权归作者**（见下节「控制权的归属」） | 只要开始写「XX 造成 YY 点伤害」，规则的控制权就从作者手里跑到了引擎里 |
| **② 让能力强的作者脱颖而出** | 用户明确在意：**卡的表达能力就是产品竞争力** | 卡格式必须留足表达空间 —— 高手能写精细的图，新手能用预设 |
| **③ 媒介优先（服务于这位玩家）** | 游戏的评判标准是「**玩家是否被满足**」，不是「世界是否自洽」 | 允许、甚至鼓励把"玩家的真实处境"纳入模拟（见下方案例） |

> ⚠️ **目标 ② 有内在张力**：既要对新作者友好，又要给强作者空间。
> 解法方向是**分层**（预设卡 → 配置模式 → 完全自定义），
> 但**不能为了友好而阉割表达力** —— 那会同时杀死目标 ② 和项目的差异化。

### 案例：「精神分析」agent（用户给的真实例子）

用户在范例卡里**一定会加一个 subagent 叫「精神分析」**，它的提示词大意是：

> 「你的玩家是一位男大学生，坐在自己宿舍的电脑前，想玩一个自由又有趣的游戏来放松一下心情，
> 请你把故事往满足他的需求的方向模拟」

**这个设计的四个含义（值得单独想清楚）：**

| # | 含义 |
| --- | --- |
| 1 | **目标函数变了**：从"世界合理"→"玩家被满足"。世界模拟降级为手段 |
| 2 | **它把游戏外的真实处境变成模拟的输入参数** —— 不只是"了解玩家角色"，而是了解**坐在电脑前的那个人** |
| 3 | **它具有自适应性质**：玩家烦躁就少添堵、玩家投入就加深沉浸（类似动态难度，但作用于氛围而非数值） |
| 4 | **它是拓扑里的一个普通节点**（作者可装可跳）—— 硬核生存卡、恋爱模拟卡可以不放它 |

> 💡 **推论**：这张卡同时也在定义「**给谁玩**」。
> 玩家的身份（大学生 / 社畜 / 硬核玩家）成了卡的一部分 ——
> 这可能是卡格式里一个此前没想到的维度。
>
> 同时它也冲击了「玩家是什么」这个待定问题（见第六节）：
> 玩家不仅是一个输入源，**玩家本身也是可以被 agent 模拟的对象**。

### 传统规则表为什么会死

```
刀伤 = HP-15、钝击 = HP-8、火伤 = 每回合 -3 …
```

玩家输入「我用湿毛巾抽他的脸」→ 规则表里没有 → 要么不认，要么硬套近似规则。

**致命后果**：玩家会迅速学会「只有引擎认识的动词才有真实后果」，
然后退回去只做那些动作 —— **自由度就是这么死的**。

而模型见过这个世界。**它的"规则表"是它读过的全部文本。**

### 项目不是在做什么

- ❌ 不是"更好的酒馆"（轮次对话 + 角色卡）
- ❌ 不是"带规则引擎的 AI 文字游戏"（规则写死，只是藏进代码）
- ❌ 不是"单模型扮演多个引擎"（见「踩过的坑」）

### ⭐ 控制权的归属（理解其余所有决定的钥匙）

用户 2026-09-13 自述：**「我是重度的控制主义者……我非常希望游戏设计者/制作者
是自己这个世界的模拟逻辑的 100% 发明人和控制者。」**

这句话定下了整个架构的价值观。三条：

| # | 原则 | 推论 |
| --- | --- | --- |
| 1 | **模拟逻辑 100% 由作者定义** | 引擎不预设任何"世界应如何运作"—— 所以没有规则表 |
| 2 | **作者主要靠提示词控制，不是靠代码** | 提示词不是"给 AI 的建议"，而是**作者用来操纵世界的编程语言** |
| 3 | **引擎只做三件事**：执行流程 / 校验格式 / 兜住坏卡 | 它**不做**任何创作或判断上的决定 |

**举例说明 #2**（用上面那个「精神分析」agent）：

```text
「你的玩家是一位男大学生，坐在自己宿舍的电脑前，想玩一个自由又有趣的游戏来放松一下心情，
  请你把故事往满足他的需求的方向模拟」
```

这段文字对作者来说**就是代码** —— 它在"编程"这个 agent 如何理解玩家。
作者不需要会写代码，他需要的是**把意图写得足够精确**。

> **关键区分：作者的 100% 控制 ≠ 玩家的自由度受限。**
> 恰恰相反 —— 作者把规则写透之后，玩家才能在作者设定的世界里**做任何事**：
> 因为所有后果都由 AI 按作者的逻辑推导，而不是被一张有限的规则表挡住。

> ⚠️ **一条架构红线**：**任何"引擎替作者做决定"的设计都是错的。**
> 例如"引擎自动推断出条件依赖哪些字段"——看着方便，
> 但它把决定权从作者手里拿走了。**该由作者声明的，就必须由作者声明。**

> 📌 **来源标注**：这条价值观由用户明确给定；本节的推论（三条原则、红线）为讨论中推导。

## 二、已决定的设计（截至 2026-09-14）

> 🆕 **2026-09-14 新增决定 #17：工具调用改用原生 tool calling。**
> 用户明确推翻旧方案（「文本协议 + JSON 代码块」），原话要点：
> *「现在是不是由模型输出，然后你代码去解析模型的输出，这样始终是有问题的！
> 应该改成你提供 tool 给模型去调用，然后返回调用结果和防呆结果，
> 让模型去调节调用格式和参数重新调用，而非你做防呆和兜底。」*
>
> | | 旧方案（已废弃） | 新方案 |
> | --- | --- | --- |
> | 工具声明 | 写在提示词里，教模型输出 JSON 代码块 | API 的 `tools` 参数（JSON Schema） |
> | 解析 | **我们自己写正则解析模型输出** | 协议层直接给 `tool_calls`，不解析 |
> | 参数错误 | 引擎「防呆」纠正／兜底 | **错误作为工具结果回传，模型自己重试** |
> | 提示词体积 | 近一半在教「工具块怎么写」 | 只剩「何时该调用」 |
>
> **为什么旧方案「始终是有问题的」**：解析模型输出本质上是在猜格式。
> 模型少写一个反引号、参数写成中文、把工具块单独发一条消息 —— 任何一处
> 都能让回合静默失败（项目为此踩过多次，见 CHANGELOG v0.5.1）。
> 原生 tool calling 把这件事变成协议契约：模型有 schema 可依，出错可重试。
>
> **代价（已知并接受）**：
> - 服务商必须在 OpenAI 兼容层支持 `tools`（主流都已支持；旧的 CORS 实测
>   只验证了「能连」，没验证「支持 tool calling」，接入新服务商时要注意）
> - 调试时「模型想干什么」不在正文字里，要看 `tool_calls` 字段
>   （界面调试模式已改为显示原始响应 JSON）
>
> **配套约束**（用户同批要求）：
> - **所有模型调用必须经过 `src/agent/llm.ts` 的 `chat()`**，别处不准直接 fetch
> - **禁止解析模型输出**：任何「从模型文字里提取结构化数据」的代码都不允许

| # | 决定 | 来源 | 理由 |
| --- | --- | --- | --- |
| 1 | **规则由 AI 判断，不写死事件表** | 用户 | 写死规则 = 退化成传统文字游戏 |
| 2 | **每个引擎交给独立 agent**，不做"单模型一轮演多角色" | 用户（旧项目教训） | 引擎一多就超出单轮输出能力，质量与格式双崩 |
| 3 | **主 agent 只做分发 / 汇总 / 格式校对**，不写故事 | 用户 | 职责分离；它的提示词全是格式约束，更短更稳 |
| 4 | **写故事的另设 agent**（数量与分工由卡决定） | 用户 | 叙事质量与编排逻辑是两种能力 |
| 5 | **启用哪些 agent 由「卡」决定** | 用户 | 恋爱模拟就不装战斗 agent；没有战斗 → 状态里根本没有血量字段 |
| 6 | **状态必须存"准确值"** | 用户 | 不存的话下一轮模型不知道发生过什么 |
| 7 | **中间状态不必保留，只存最终状态** | 用户 | HP 100→88→61→44，中间那三个值对游戏没有意义 |
| 8 | **"回合"是人为的玩家干预点**，不是世界的属性 | 用户 | 世界连续演化，"停下来等玩家"只是为了参与感 |
| 9 | **一轮的执行流程由卡作者写死**：调用哪些 agent、什么顺序、什么条件走哪条路 | 用户 | 作者理应握有这个控制权；**流程固定 = 调用次数可预测** |
| 10 | **条件分支允许**，语义是「**这个对象/这个判断在本轮是否需要**」 | 用户（纠正了 AI 的错误设想） | 角色不在当前场景 → 没必要每轮模拟他。反例见下方注释 |
| 11 | **上下文默认全敞开给所有 subagent** | 用户 | 信息对称，避免各算各的；用成本换准确性 |
| 12 | **卡可以自定义 agent 本身**（名字、提示词、职责、读写哪些状态） | 用户 | 世界状态量都由作者定，agent 自然也该由作者定 |
| 13 | **故事创作由多个 agent 协作完成**，具体几个、各干什么，也由卡决定 | 用户 | 不同作者有不同想法，**引擎不规定创作结构** |
| 14 | **「关键时刻」不是引擎规则，而是提示词层的偏好** | 用户 | 体现为大纲 agent 的一句预制提示词（「尽量让故事停在关键的时刻」）。**引擎里什么都不用做** |
| 15 | **输出格式标准化 + 可自定义** | 用户 | 状态格式有预设、作者可覆盖；显示格式由作者声明 |
| 16 | **一轮的边界 = 图执行完毕**（不是"演化到满足某条件"） | 讨论中推导 | 与 #9 配套：流程走完就停，无条件把控制权交还玩家 |
| 17 | **工具调用改用原生 tool calling**（见上方说明块） | 用户 | 解析模型输出始终会猜错格式 |
| 18 | **界面用 Tailwind CSS 4，不再手写 CSS** | 用户（"就他吧"） | 现代外观 + 深浅色模式；语义 token 集中在 `src/styles/main.css` |
| 19 | **中英双语，且模型语言跟随界面语言** | 用户 | 中文只存在于 locale 文件；代码一律 ASCII |
| 20 | **提示词按语言分目录，构建期编码后随包发布** | 用户 | `prompts/<lang>/*.md` → 虚拟模块（base64），仓库里不存生成物 |
| 21 | **分层：界面 = f(state)**（见下方说明块） | 用户 | `game/` 与 `agent/` 都不依赖 Vue，Vue 只在 `stores/` |
| 22 | **一条事件流 + 三种投影**（故事与调试同流，界面按调试开关过滤） | 用户 | 没有第二个可变显示数组，就没有「写进去忘了收回」的行；顺序天然正确 |
| 23 | **UI 自动化分四层**：单元 → 组件故事（Storybook）→ 功能冒烟 → 视觉矩阵（Playwright） | 用户 | 一次把基础打好：组件当工作台看，断言与截图统一由 Playwright 做 |
| 24 | **沉浸式布局：文字是主线，控件都浮起来**（见下方说明块） | 用户 | 顶栏 + 侧栏 + 页脚式的排布「太像一个办公软件」 |
| 25 | **示例卡的默认图是线性 9 节点**（并行 / 循环 / 条件 / 扇出 / 采样当前不做，见下方说明块） | 用户 | 机制留着，先把一条能跑的直线搭出来；线性图的成本上限天然 = 节点数 × 1 |
| 26 | **节点上下文 = 公共部分 + 本轮上游累加**（`提示词.节点约定` 也进上下文，见下方说明块；逐节点上游不写进卡，由拓扑推 —— 见 #40） | 用户 | 设定与历史人人有份，本轮的结论按拓扑顺序往前传；⑥ 角色要读得到 ⓪ 精神分析的名单 |
| 27 | **一轮是一个事务**：节点只读写工作副本，提交是权威状态的唯一写入（见下方说明块） | 讨论中推导 | 中途报错不至于"世界更新了一半" |
| 28 | **玩家 / 主控是两个东西**：玩家在世界之外，主控在世界之内（见下方说明块） | 用户 | "玩家在世界之内"这句话自相矛盾；分开才说得清谁被模拟、谁被显示 |
| 29 | **主控的强度与「谁会死」由卡决定**，引擎不规定（见下方说明块） | 用户 | 引擎只提供机制；"能代入的普通人"是《晨风镇》的选择，不是引擎的规则 |
| 30 | **状态里存事实，不存结论**（属性 / 伤势 / 硬币 / 关系，见下方说明块） | 用户 | 能算出来的就别存 —— 存了汇总值就等于把规则表请回来 |
| 31 | **开局不写死正文**：作者写「开局要求」，开场由 AI 现写（见下方说明块） | 用户 | 写死 = 每局一模一样，重开两次就腻了 |
| 32 | **世界地图分三层**：区域 / 地点 / 场景（见下方说明块） | 用户（来自旧项目） | 三层各管一件事：演算边界 / 存在性与持久化 / 叙事舞台 |
| 33 | **卡给「种子」，不给「边界」**：生成器是卡里的一等公民（见下方说明块） | 用户 | 清单会过时、会长不全、会挡住玩家；种子不会 |
| 34 | **卡的存储格式是 JSON**：一张卡 = 一个自包含的 `.json` 文件（见下方说明块） | 用户 | 零依赖、`git diff` 干净、表达力够 —— 而且作者根本不手写它 |
| 35 | **卡 ID = `作者名.卡名`**，导入与存档靠 ID + 卡名 + 版本核对（见下方说明块） | 用户 | 纯前端没有注册表，防不住重名 —— 那就让碰撞可检测 |
| 36 | **上下文裁剪 = 公共部分 + 本轮上游累加**（`contextFor` 纯函数；拿不到上游就不猜，见下方说明块） | 用户 | 落地 #26；无上游时与旧快照逐字节一致，阶段 3 照图跑时只换调用方 |
| 37 | **执行器只认图与上游，不认卡**（`Graph` / `GraphNode` 是最小执行单位；默认图 = 1 节点，验收方式见下方说明块） | 阶段 3 | 卡是数据、执行器是机制：把卡的解析塞进执行器，卡格式一改就要动机制 |
| 38 | **节点进度走调试通道**：执行器的 `node` 事件转发成 `AgentEvent`，**调试模式才**写成一行痕迹（玩家可见的故事与状态行不变） | 阶段 3b | 引擎不认识调试模式；「谁能看到」由投影决定（#22）—— 进度是给开发者的过程信息，不是玩家的故事 |
| 39 | **事务边界在组合根**：回合跑在工作副本上，跑到终点才一次性写回 + 落盘；失败 / 取消丢弃副本，内存与存档都不留痕（见下方说明块） | 阶段 4 | #27 的落地位置：引擎不认事务，「拷副本 / 提交 / 落盘」是持有权威状态与存储的组合根的事 |
| 40 | **卡格式 card/2**：顶层按「谁读」分三块（`声明` / `提示词` / `说明`），执行顺序只由 `声明.图.拓扑` 声明一次 | 用户 | 一份数据一个读者，边界可检查；删掉「序号 + 数组顺序」这两份重复，散文里也不再放机器数据（见下方说明块） |
| 41 | **回合生命周期是一张迁移表**：`idle` + 运行中四阶段（`prompting` / `executing` / `forcing` / `finishing`）+ 终态 `committed` / `rolled-back`，合法性只在 `advance()` 一处判断（见下方说明块） | 阶段 5 | 只有 `finishing` 能提交、失败与取消只能从运行中阶段回滚 —— 由表保证，不靠调用方自觉；状态行是它的投影（#22） |
| 42 | **开局事实由卡声明**：`起始时刻` / `初始位置.场景` / `默认名` 进新游戏的第一帧，引擎只认这三样（`可让玩家起名` 暂不消费；见下方说明块） | 阶段 6a | 卡已经声明了这些事实，写死的初始状态等于让作者的话落空；没有消费者之前不扩张状态形状 |

### 决定 #19：语言（i18n）

| | 做法 |
| --- | --- |
| 语言状态 | `system` / `zh-CN` / `en`，与主题一样三态循环，存 localStorage |
| 文案存放 | **只有** `src/locales/*.json`；界面一律 `t('some.key')` |
| 代码语言 | 代码一律 ASCII（含字符串、标识符、对象键）；中文只允许在 locale、`prompts/*.md`、`doc/`、注释里 |
| 模型语言 | **跟随界面语言**：切到 English，GM 就用英文写、提示词也换英文那套 |
| 强制 | `.githooks/checks/ascii.mjs`（字符串里的中文也拦）+ `identifiers.mjs`（标识符必须英文） |

**为什么模型语言要跟随界面**：卡的语感是玩家选的。界面英文而 GM 回中文是**语言混杂**，
不是"国际化"。代价是每种语言的提示词要单独维护（英文提示词目前是机器翻译的初版，
见 `prompts/README.md`）。

**为什么标识符也必须是英文**（用户明确要求，没有"领域词汇例外"）：
中文标识符没有词边界、grep 困难、对不读中文的人是乱码。

### 决定 #20：提示词的存放与编码

源文件是 `prompts/<lang>/*.md`，由 `vite-plugins/prompts.ts` 在**构建期**转成虚拟模块
`virtual:prompt/<lang>/<name>`，内容是 **base64**。

- **为什么不直接 `?raw` 引入**：反引号、`${`、换行、引号、中文在字符串里都要转义，
  任何一处漏了都是运行时故障；base64 彻底避开转义坑。
- **为什么不留生成文件**：仓库里存一份 `.b64` 就多一个"忘了重新编码"的失败模式
  （改完 `.md` 忘了跑脚本）。虚拟模块不存在这个问题。
- ⚠️ **这是编码不是加密**：客户端字符串永远拿得到，别把需要保密的东西放进去。
- 运行时按当前语言选提示词（`currentLocale()`），中英各一套。

> **#10 的反例（留着防复发）**：「战斗命中 → 才调角色 agent」是**错的** ——
> 挨了一刀哪怕躲过去，角色也有反应（心跳、重新评估对手、退半步）。
> 条件的正确用途是**存在性判断**，不是**结果判断**。

> **由 #14 得到的副产品**：**叙事性判断绝对不要写成引擎规则。**
> 写规则就得写 `if 玩家HP<30 && 敌人HP<30`，那是传统游戏的写法，
> 而模型自己就懂"什么叫戏剧性"。**能交给 AI 判断的，就不要写成规则** —— 这是 #1 的又一次应用。

### 决定 #21：分层与依赖方向

**界面 = f(state)**。领域是**纯数据 + 纯函数**，界面唯一的数据源是它：

| 层 | 位置 | 职责 | 允许依赖 |
| --- | --- | --- | --- |
| 领域数据 | `src/game/state.ts` | `GameState` 是**普通接口**（`data` + `loadError`）；动作是纯函数 `addLog(s, …)` / `advanceTime(s, …)` / `save(s, store)` | 不依赖 Vue |
| 校验 | `src/game/save.ts` | 一份存档的形状与校验（外部数据出界） | 不依赖 Vue |
| 模型侧 | `src/agent/` | 拼提示词、调模型、执行工具、跑回合；只接 `AgentContext`（纯数据 + 三个动作） | 不依赖 Vue |
| 投影 / 组合根 | `src/stores/` | 把纯数据包成 `reactive`、决定什么时候落盘、暴露派生与动作给组件 | **Vue 只出现在这一层** |
| 界面 | `src/components/`、`src/App.vue` | 只渲染、只发意图 | 只读 store 的派生，只调 store 的动作 |
| 基础 | `src/utils/`、`src/i18n.ts` | 纯函数（历法、存储）与文案表 | 不依赖上面任何一层 |

**为什么是函数而不是类**：类本身没问题（167 行数据 + 方法，很薄），但**类 + Vue 响应式**
有三处结构性摩擦，都在这个项目里实测踩过：

- `private` 字段会让类在 TS 里「不可结构化」，而 `reactive(初始状态)` 的类型
  正是取它的结构 → `store.game` 推不出原型方法，界面层类型全崩；
- 改成 `#private` 更糟：Vue 的代理不在私有品牌里，方法一访问就抛错；
- 于是存储适配器只能做成**公开字段** —— 数据自己攥着一个存储句柄，
  「谁负责落盘」变成每处都要读代码才能回答的问题。

纯数据没有这些负担，而且领域逻辑能在没有 Vue 的地方跑（离线脚本、卡校验）。

**六条约束**：

1. **动作函数原地改传进来的 `s`，不返回新 state。** 调用方把 `reactive()` 的**代理**
   传进来，Vue 才能建立依赖；传原对象（`toRaw`）不会报错，但界面不会更新 ——
   这类静默失败由 `tests/store.test.ts` 的「改数据 → DOM 更新」用例守着。
2. **响应式边界在 `src/stores/`** —— `game/`、`agent/`、`utils/` 都不 import Vue，
   所以它们能在 Node 里直接测，也保留了把引擎单独抽出去的可能。
3. **组件不写状态** —— 组件只读 store 的派生、只调 store 的动作；
   写状态是领域函数（`advanceTime(s, …)` / `addLog(s, …)`）。
4. **依赖单向**：界面 → 投影 → （领域 / 模型侧）→ 基础。反向依赖一律不允许
   （基础层不认识游戏，领域不认识模型）。
5. **存储是参数，不是状态的一部分** —— `save(s, store)` / `importFile(s, json, store)`；
   引擎（`agent/`）完全不碰存储，落盘由组合根在回合成功后决定。
6. **开发工具不进产物** —— 卡图（`src/dev/card-graph.ts` + `src/components/CardGraph.vue`）
   是作者 / 调试工具，只被 Storybook 故事引用，`src/App.vue` 与 `src/main.ts` 都不引它；
   `@vue-flow/core` 因此装在 **`devDependencies`** —— 只在 Storybook / dev 里用，
   `npm run build` 的 dist 里没有它（玩家侧依赖仍然只有 `vue`）。

**为什么这样分**：一个文件能一句话说清职责才算分了层。
把「建默认局 + 出界校验 + 读写 + 格式迁移」四件事写在一个文件里的代价是：改一处要读全文。
拆成「纯数据 + 纯函数（game/state.ts）+ 形状校验（game/save.ts）+ 存储适配（utils/storage.ts）」之后，每层都能单独测、单独替换。

### 决定 #22：一条事件流 + 三种投影（界面显示 = 真值的函数）

**起因是两个实测 bug**（都在真机复现过，不是推测）：点「重来」后
「正在生成开场…」永不消失；刷新后「继续游戏（第 N 回合）」赖在故事中间。
根因相同：故事区是一个**有人 push、没人负责寿命**的数组，里面混着四种寿命完全不同的内容 ——
最短命的（进行中）按最长命的（永久）活着，于是必然出现「不消失」。

**修法不是「记得删掉占位符」，而是让「显示」永远是某个真值的投影。**

| 内容 | 判据 | 住在哪 | 谁能看到 |
| --- | --- | --- | --- |
| 叙事 / 玩家行动 / 回合标记 | **已经发生**的事 | `data.events`（`narration` / `action` / `system`） | 玩家 + 模型（`system` 只给模型） |
| 模型 I/O、工具调用与结果、引擎警告、节点进度 | 只有开发者要看 | **同一个** `data.events`（`request` / `reply` / `tool` / `toolResult` / `warn` / `node`） | 只有打开调试模式的开发者 |
| 进行中（正在生成 / 思考中） | 只在此时此刻成立 | `phase` → `status`（computed） | 玩家（回合结束即消失） |
| 通知（导出完成 / 保存失败 / 存档已导入…） | 一次性提示 | `notice`**单槽**（computed 读取） | 玩家（下一条覆盖它；回合开始清空） |

**四条规则**（改界面时必须守）：

1. **只有一个事件流。** 故事与调试痕迹写在**同一个数组**里 —— 顺序就是它们发生的顺序，
   所以调试行会精确地插在它发生的那段叙事之间，而不是被堆到末尾。
   谁看得到由**投影**决定，不由存储位置决定：
   `rows`（界面，按调试开关过滤）/ `snapshot()`（模型，只取故事类）/ 存档（全量）。
2. **上限按类分别计**（故事 80 / 调试 120，见 `game/save.ts` 的 `trimEvents`）：
   调试噪声**不许**把模型记忆挤掉 —— 只按总条数裁就会出这个问题。
   模型快照也必须显式过滤（`isStoryKind`），因为刷新后它正是读事件流。
3. **不许有第二个可变的显示数组。** 想临时显示点什么，就去通知，不许写进事件流。
   判断标准只有一句：**它是「已经发生的事」吗？** 不是就不属于事件流。
4. **调试模式：本机开发默认打开，且可以随时关掉**（入口按 `location.hostname` 判定
   `localhost` / `127.0.0.1` / `[::1]`）：本地能看到模型输入输出与工具调用；
   顶栏的开关（**只有本机地址才有这个按钮**）可以关掉它去看「非调试的正常界面」，
   关掉的选择会被记住（刷新不会自己打开）。线上域名两条都不命中 ——
   玩家既没有开关、也不会看到模型 I/O；调试开着时顶栏一定有标记说明那些额外行不是 bug。

**为什么调试痕迹也进存档**（而不是另开一个键）：它**也是「已经发生的事」**，
就该和故事同一条时间线 —— 分两个数组就得再造一套编号去对齐位置，而那套对齐永远会漂。
它也**必须扛得住刷新**：排查问题时最需要看的就是上一个回合模型到底收到/发出了什么。
代价是存档变大（上限管住了它），换来的是「顺序天然正确」和「一个键、一份真相」。

**为什么不是「记得删掉占位符」**：那只是消灭这一次的实例 —— 数组还在、寿命规则还是没有，
下一个人照样会写「正在导入…」。改成投影之后，「push 进去指望别处收回」这个**形状不存在**，
不需要新增纪律、也不需要谁记住规则。这是 #21「界面 = f(state)」在显示层面的直接应用。

**已经删掉的**：`继续游戏（第 N 回合）` 这条通知。它把「接着上次玩」这个**默认行为**
当成事件播报，而且回合数是**写进去的快照**（侧栏那个才是响应式的）——
同一事实两处表示。留着的通知都只描述「刚刚做完的一件事」（导出完成 / 保存失败 / 存档已导入）。

**还没做的**（写在这里免得被当成已完成）：回合的**阶段**（prompting / executing / forcing /
finishing）目前仍是 `while` 循环里的隐式状态 —— 显式状态机是下一步（见「待定」）。
节点进度（决定 #38）只让开发者在调试模式下看见「轮到哪个节点」，不等于阶段有了状态。

### 决定 #23：UI 自动化的四层

| 层 | 工具 | 管什么 | 命令 |
| --- | --- | --- | --- |
| 单元 / 组件 | vitest + @vue/test-utils | 纯逻辑、props 契约（跑在 node/jsdom 里，快） | `npm test` |
| 组件故事 | Storybook 10 当**工作台**，Playwright 当**断言与相机** | 每个组件的每个状态 × {浅,深} × {中,英} | `npm run stories` |
| 功能冒烟 | Playwright | 玩家点得出来的路径（设置、语言、主题、坏存档、跑一个回合…） | `npm run e2e` |
| 视觉矩阵 | Playwright | 10 个状态 × 5 种屏幕：结构检查 + 少量像素基线 | `npm run visual` |

**为什么 Storybook 与 Playwright 各管一段**：Storybook 提供「组件工作台」（浏览、controls、
a11y 面板），但它的自动化测试入口（addon-vitest）要求 vitest 3/4，而本项目在 vitest 5 上；
硬凑不值得。断言与截图统一交给 Playwright：**同一套结构判据、同一套基线机制**，
不引入第二套快照格式。（`npm run storybook` 起来看，`npm run stories` 跑巡检。）

**结构判据只有三条**（客观、无基线）：横向溢出、元素伸出视口、点按目标 < 24×24
（WCAG 2.5.8，含「句子里的行内链接」例外）。样式好不好看只能靠看图 ——
`artifacts/screenshots/index.html` 与 `artifacts/stories/index.html` 是给人（和会看图的模型）看的。

**基线策略**：只给 **8 张整页画面**建像素基线（稳定的、看过的），组件故事不建 ——
组件改动频繁，基线会变成天天刷新的噪音。基线进仓库（652KB），刷新要显式
`--update-snapshots`。

**已知的下一步**：界面还不够沉浸（顶栏按钮多、侧栏重、缺动画）——
这是 #24 要解决的问题，UI 巡检这一层正好用来看改动前后的差别。

### 决定 #24：文字是主线，控件浮起来

用户的原话：*「为了增加沉浸感，文字应该是主线，输入框做成悬浮，设置做成悬浮的小按钮，
右侧边栏的状态也要缩小，最好也悬浮起来，现在太像一个办公软件了。」*

| 原来 | 现在 |
| --- | --- |
| 顶栏一条：品牌 + 状态文字 + 主题/语言 + 导出/导入/重来/设置 | **两颗悬浮小按钮**：设置（带连接状态点）、调试（本机开发才有） |
| 右侧一列三张卡片（时间 / 地点 / 回合 + 时间线） | **左上角一小块浮层**：时间、地点 · 回合，加最近一次时间跳跃 |
| 输入框是页脚（贴着底边、占一条） | **悬浮卡片**：半透明 + 毛玻璃 + 阴影，文字从它下面滚过去 |
| 主题 / 语言在顶栏，存档操作分散 | 全部收进设置面板（同一个三态控件风格） |

**四条约束**（改这块时要守）：

1. **故事区占满整屏**，是唯一的主线；别的都是它上面的浮层（`absolute`）。
2. **浮层不许挡住正文**：故事区自己留出上下内边距（`pt-20 pb-32`），
   阅读列居中（`max-w-[68ch]`）—— 这是「像在读小说」的关键。
3. **动效服务于阅读**：新行淡入 + 轻微上浮（420ms，`偏好减少动效`时关掉），
   背景一道极淡的光晕。**不做**炫技式的位移/缩放 —— 那是干扰。
4. **功能不许因为「收起」而消失**：主题与语言搬进设置面板，存档三件套也都在那儿。

**代价（已知）**：设置入口从「一眼可见的按钮」变成「两颗小按钮里的一颗」，
新玩家要先找到它（所以没配 API 时，输入框上方仍留一行指引，直说「点右上角设置」）。

### 决定 #37：执行器只认图与上游（阶段 3）

`src/agent/graph.ts` 是最小执行器：**节点 = id + 一个 run 函数**，**图 = 有序节点数组**。
它只做三件事 —— 按顺序跑节点、把已跑完节点的产出按顺序作为上游交给下一个、出错原样上抛；
取消时抛 `AbortError`，后面的节点一个都不跑。**它不认卡**：卡到图的翻译（读 JSON、按拓扑
排节点、把节点提示词接成 run）是后面的事，执行器里没有一处 `card`。空图**抛错**，
不返回空结果 —— 零个节点的「成功回合」会静默掩盖坏卡。

**为什么分开**：卡是声明式数据，执行器是机制。解析塞进执行器，卡的字段一改就得改机制；
校验卡（`src/game/card.ts`）跟执行无关，两边各管各的。

**默认图 = 1 个节点**：`runTurn` 内部构造一张只有一个节点的图，那唯一的节点就是 agent
循环，它的产出就是本回合的叙事正文。九节点卡片图本阶段不接。

**「行为不变」怎么验收**：既有 333 项测试**一行不改**全绿（新增测试只测执行器本身：
3 节点顺序与上游、抛错上抛、取消、单节点、空图）。执行器回传的 `node` 进度事件
现在会转发给调用方，并在调试模式下成为一行痕迹 —— 见决定 #38。

### 决定 #38：节点进度走调试通道（阶段 3b）

执行器每进一个节点回传一次的 `node` 事件（`{ type: 'node', id }`）**接到了界面这条通道上**：
`runTurn` 把它原样转发成 `AgentEvent`，`stores/turn.ts` 只在**调试模式打开时**写成一行调试痕迹
（kind `node`、文案键 `store.nodeLine`，位置就在这一轮的开头 —— 它确实发生在最前面）。

**为什么写不写痕迹由界面侧决定**：引擎（`src/agent/`）不认识调试模式，也不该认识 ——
它只负责把「轮到哪个节点」告诉调用方；「谁能看到」是投影的事（决定 #22）。
所以 `node` 事件是**瞬态的进度**：不写日志、不改状态。调试关掉时，事件流与玩家看到的
故事、状态行一个字节都不变；调试打开时，它和其他痕迹一样落在同一个数组、同一条时间线上
（#22 的四条规则不变，上限仍按调试类计数）。

**为什么玩家看不到也没关系**：这是给作者 / 开发者看「卡跑到哪了」的工具，不是玩法 ——
这一行只在调试模式里出现，线上域名既没有开关也不会打开（#22 规则 4）。

**为什么不是复用 `thinking`**：`thinking` 表达「模型第几步」，`node` 表达「轮到哪个节点」——
九节点图上两者会同时出现，混用就丢掉一个维度（`src/agent/graph.ts` 的注释）。

**顺带**：dev-only 的卡图（`src/dev/card-graph.ts`）那组显示模型改名为
`CardGraphLayout` / `LayoutNode` —— 它与执行器的 `Graph` / `GraphNode` 同名不同义，
两组都 import 的文件（如测试）很容易看错。

### 决定 #39：事务边界在组合根（阶段 4）

决定 #27（一轮是一个事务）的落地位置是 `src/stores/turn.ts` —— 它是持有权威状态、
响应式与存储的组合根；引擎（`src/agent/`）完全不认识事务，它照旧原地改拿到的对象。

| 时刻 | 做什么 |
| --- | --- |
| 开跑前 | `structuredClone(toRaw(state.data))` 拷一份**工作副本**，把承载副本的 `GameState` 交给 `runTurn` |
| 跑的时候 | 引擎、工具、调试痕迹全部只写副本；权威状态一个字节都不动 |
| 成功 | `state.data = draft.data` —— **一次赋值 → 响应式一次触发**，随后 `save()`（它读的是权威状态，所以提交必须先于落盘） |
| 失败 / 取消（AbortError） | 丢弃副本：既不写回也不落盘 |

**为什么克隆要先 `toRaw`**：`state.data` 是 `reactive()` 代理，而 `structuredClone`
遇到 Proxy 直接抛 `DataCloneError` —— 这不是防御性代码，是必需的一步。

**落盘失败的语义不变**：`save()` 返回 false 仍然是「回合成功了，但没写进去」，
由组合根通知玩家（状态行的错误提示）。事务只管「内存与存档要么一起有、要么都没有」，
不管存储本身写不写得进去。

**【用户可见的变化】叙事现在在回合提交时才出现在故事区**（以前是每一步实时出现）。
这是事务的直接代价：实时写 = 把**未提交**的改动先摆给玩家看，而取消或失败之后它会消失
—— 玩家看到的是「写了又没写」。侧栏的时间与时间线同理：推进发生在提交那一刻，不是
工具调用的那一刻。在「显示源就是权威状态」这条约束（决定 #22）下，事务与「边跑边显示」
不可兼得。

> 备选（**不实现**，只是记下来）：给本轮未提交的叙事开一个**瞬态预览槽**
> （不属于事件流，提交后丢弃、失败后清空），界面把预览行渲染在故事末尾。
> 它能同时保住事务与实时显示，代价是引入第二个可变显示源 —— 正是决定 #22 要消掉的东西
> （多一类「写了要记得收」的行，而且它和真实事件流会有两份内容需要对齐）。

### 决定 #40：卡格式 card/2 —— 顶层按「谁读」分三块，顺序只声明一次

**顶层只有 4 个键**：`卡`（元信息）+ `声明` / `提示词` / `说明`。

| 块 | 谁读 | 里面是什么 |
| --- | --- | --- |
| `声明` | **代码** | 图（拓扑 + 节点）/ 状态 schema / 世界 / 生成器 / 开局事实 / 显示 |
| `提示词` | **模型** | 设定（五块）/ 剧本 / 节点约定 / 逐节点提示词 / 开局要求 |
| `说明` | **人** | 状态 / 剧本 / 开局三块的块级说明（字段级的「说明 / 禁止」仍内联在原处） |

**为什么值得一个格式版本**：这不是审美分类，是**可检查的硬边界**。
同一样东西被三种角色读，混在一块时「这句话是给谁看的」只能靠命名习惯维持；
分开之后，键的位置本身就说明了读者，校验器也照着这条边界守
（`声明.图.拓扑` 是唯一的顺序声明、`说明.状态` 必须跟 schema 的段名对得上）。

**顺序只声明一次**：执行顺序 = `声明.图.拓扑`；节点本身没有 `序号`，也不看数组顺序。
card/1 把顺序写在两处（节点数组顺序 + 每个节点的「序号」），
再加上散文里那 9 行「· ④ time 公共部分 + ⓪①②③」—— 同一件事写三遍，
改一个节点要同步三处，漏一处就是「图跟散文说的不是一回事」。

**散文里不再放机器数据**：节点约定里那 9 行逐节点上游删掉了 —— 它是**派生内容**
（上游 = 拓扑前缀，决定 #26），由 `tools/render-card.mjs` 渲染时现推，
人读的 `cards/晨风镇.md` 里一行不少。卡是事实来源、md 是产物，派生行不该住在事实来源里。

**为什么没有 `读` 字段**：决定 #26 已经定了「上游 = 拓扑里排在它前面的全部节点」，
每个节点再抄一遍同样的清单是零信息的重复；卡图（`src/dev/card-graph.ts`）直接按拓扑前缀算读边 ——
9 个节点 36 条，虚线上一律不写字（写字会糊成一团）。

**代价（已知并接受）**：节点提示词从「节点数组里的一项」变成 `提示词.节点[<id>]`，
于是**改一个节点要看两处**：`声明.图.节点[<id>]`（它是什么）与 `提示词.节点[<id>]`（它该干什么）。
换来的是两边的读者不同、校验器分别守，不再有一个「既是数据又是提示词」的混合体。


### 决定 #41：回合生命周期是一张迁移表（阶段 5）

一轮的阶段从控制流里搬出来，变成 `src/game/lifecycle.ts` 里的**数据**：状态、事件、迁移表
各一份。`advance(state, event)` 是纯函数，表外的组合**直接抛错** —— 状态机与真实执行一旦
悄悄分叉，「回合在飞」这个判据（重入保护与状态行都靠它）就不再可信。

| 阶段 | 什么时候 | 允许的事件 → 下一阶段 |
| --- | --- | --- |
| （空闲） | 没有回合在飞 | `start` → prompting |
| prompting | 请求模型（第一步与多步循环里的每一步） | `request-model` → 自身；`call-tools` → executing；`force-narration` → forcing；`closing-text` → finishing；`rollback` → rolled-back |
| executing | 执行模型这一步要求的工具调用 | `call-tools` / `tools-returned` → 自身；`request-model` → prompting；`force-narration` → forcing；`closing-text` → finishing；`rollback` → rolled-back |
| forcing | 步数用尽、还没写过叙事 —— 不给 tools 补写一次 | `closing-text` → finishing；`rollback` → rolled-back |
| finishing | 收尾文字到手，事务还开着 | `commit` → committed；`rollback` → rolled-back |
| committed / rolled-back | 终态 | `reset` → （空闲） |

**边界取引擎里真实存在的等待点**：`prompting` 与 `executing` 的自环都是真的 —— 多步循环里
下一步的请求仍在请求阶段，而一次模型消息可以带多个工具调用，结果一条条回来。

**两条由表保证的性质**：只有 `finishing` 能 `commit`（正文到手才提交，决定 #27/#39）；
失败与取消只能从四个运行中阶段 `rollback`。终态只活到 `reset`（`runTurnAction` 的 `finally`），
所以「回合在飞」= `isRunning`，界面的输入禁用与状态行都读它；状态行的文案键由
`statusKeyOf` 给出，翻译留在组合根（显示是派生值，决定 #22）。

**与最初设想的三处差异**（都以代码里真实存在的路径为准）：

1. **给引擎加了一个瞬态事件 `forcing`**：补写那次请求不带 tools，它既没有 `thinking`
   也没有 `model`，事件流里唯一的痕迹是那条本地化的 `warn` 文案 —— 拿显示文案驱动状态
   等于让显示决定行为（与 #22 反向），而且失效是静默的。新事件与 `thinking` / `node` 同类：
   不写日志、不改游戏数据。
2. **`finishing` 取「`runTurn` 交回正文」这一刻**，而不是「模型最后一条回复没有工具调用」：
   补写请求根本不产生 `model` 事件；而步数用尽但已经写过叙事时，回合是带着 `executing`
   收尾的（所以表里 executing 也接受 `closing-text`）。
3. **`rollback` 允许从 `finishing` 发生**：那时正文到手但一个字节都还没写回，事务仍然开着。

### 决定 #42：开局事实由卡声明，引擎只认这几个字段（阶段 6a）

新游戏的第一帧不再由引擎凭空造：`声明.开局` 说什么，第一屏就是什么。

| 卡里的字段 | 进哪 | 说明 |
| --- | --- | --- |
| `起始时刻` | `time.iso` | 卡里写成 `YYYY-MM-DDTHH:mm`（**本地**时刻，不带时区）；原样存，`Date` 认它 |
| `初始位置.场景` | `scene.name` | 只取场景 —— 区域与地点这一阶段没有消费者 |
| `默认名` | `player.name` | 空串 = 卡没给名字，退回 i18n 的 `player.defaultName` |
| `可让玩家起名` | —— | **这一阶段不实现交互**：起名界面还没有，没有消费者 |

**只做「第一帧由卡决定」，不扩张状态形状**：`GameData` 的六个键一个不加，
角色 / 地图 / 背包留给后面的阶段。理由就是反过度工程：**没有消费者就不先建树** ——
一个没人读的字段不但要写、要校验，还要在每次改状态形状时被重新审视。

**读档优先级不变**：存档里有 `time` / `scene` / `player` 就用存档的，卡的开局只管新游戏；
读档缺字段时补的仍是 `createInitialState()` 的形状默认值（当前时刻 / 空场景名 / i18n 默认名）。

**坏卡启动即失败**：`src/game/current-card.ts` 在模块加载时校验静态 import 的那张卡，
校验不过应用就起不来。引擎读哪几个字段，`card.ts` 的 `checkOpening` 就守哪几个 ——
形状只在系统边界判一次，`opening.ts` 只做字段映射、不重判类型。

**纯函数边界**：`src/game/opening.ts` 的 `openingOf(card)` 只把开局翻译成
「时刻 / 场景名 / 默认名」三样事实，不 import Vue、不认 i18n；默认名的兜底留给调用方。

**`now` 这种写法没实现**：「卡的元信息」一节记过起始时刻可以有「具体时刻 / `now`」两种写法，
现在只有具体时刻 —— 没有消费者就先不开这个口子，卡里写 `now` 会被校验器拒（快速失败）。

## 三、讨论中得出的关键洞察

### 洞察 1：回合长度应该是自适应的（动机）

玩家输入"砍一刀"，**不能只模拟这 5 秒然后停下来等下一刀** —— 那太蠢了。

一个遭遇战应该被连演几个来回，演到一个值得让玩家重新决策的位置再停。

**动机与实现要分清：**

| | 内容 |
| --- | --- |
| **动机** | 固定切片（一次模型输出 = 一回合）会让节奏碎掉 |
| **最终实现** | **不是**引擎动态探索（那会引入"何时停"的判断难题），**而是作者在图里声明**（决定 #9/#16）：比如"战斗节点循环 3 次" |

也就是：**"自适应"这件事由作者的设计体现，而不是由引擎的智能体现。**

### 洞察 2：时间与事件是**反馈环**，不是流水线

```
时间 agent 判「过了多久」→ 需要知道「打了几个来回」
战斗 agent 判「几个来回」→ 每个来回都要知道「这之间过了多久」
```

旧做法是把环剪断：**先算时间、划定模拟范围，再让其他引擎在这个范围里跑**
（用户旧项目的做法，也是固定切片的来源）。

多 agent 架构的价值之一：**这个环可以保持成环** —— 让 agent 互相问。

> **这解释了"为什么同一个 agent 会被反复调用"**：不是设计缺陷，是反馈环的必然结果。

### 洞察 3：同一 agent 被多次调用的**五个**来源

| 来源 | 机制 | 例子 |
| --- | --- | --- |
| 常规工序 | 每轮都要问 | 时间 agent |
| 聚合调用 | 同类判断有多个对象 | 场景里 3 个 NPC → 角色 agent 调 3 次 |
| **条件触发** | A 的输出决定要不要走 B | 战斗判"重伤" → 才需要评估"伤势对后续行动的影响" |
| **多阶段流程** | 同一件事先后问两次 | 先"预判后果" → 执行 → 再"结算实际发生" |
| **采样** | 同一件事**要多个候选** | 故事 agent 产出多个大纲，挑最好的（见洞察 6） |

后三个是网状结构的真正来源：**串并联只能表达固定顺序，网状才能表达"结果决定路径"。**

### 洞察 4：中间状态 = 黑板模式

```
图执行期间（内存工作副本，不落盘）      图执行完毕后（提交为权威状态）
HP 100 → 88 → 61 → 44              只存 HP 44
轻伤 → 重伤 → 骨折                  只存 左臂骨折
```

**两个东西要分清**（此前文档把它们混在一起，是错的）：

| | 工作副本 | 权威状态 |
| --- | --- | --- |
| 活在哪 | 内存，本轮有效 | 存档，跨轮有效 |
| 谁能读 | **本轮所有 agent** | 下一轮的 agent（作为起点） |
| 谁能写 | 各 agent 的输出经主 agent 合并后写入 | 只有"提交"这一步写 |
| 轮末 | **丢弃中间态**，只留最终值 | 成为下一轮的起点 |

- **写冲突的防线**：中途写的是工作副本，"谁能改权威状态"只有一条路（提交），
  所以不需要复杂的锁机制 —— 冲突只会发生在"同一个字段本轮被两个 agent 都改了"，
  这由**主 agent 合并**时解决（见待定 5）。

### 洞察 5：调用拓扑就是玩法

同一个世界、同一批 agent，**换个拓扑就是另一个游戏**：

| 游戏类型 | 拓扑特征 |
| --- | --- |
| 恋爱模拟 | 无战斗 agent；角色 agent 高频多次；存在性条件看好感度 |
| 侦探推理 | 时间权重极高（时限压力）；"证据齐了才能指认"是条件门槛 |
| 生存恐怖 | 时间 + 资源消耗每轮必跑；"受伤→感染→恶化"是链式触发 |

**所以卡作者写的不是"设定"，是"规则拓扑"。**

### 洞察 6：引擎不规定「创作结构」

「故事要几个 agent、先写大纲还是直接写、要不要多方案挑选」——
**这是创作方法论，不同作者有不同做法**（用户 2026-09-13 明确：先不预设）。

引擎只提供机制（能并行、能条件、能循环、能采样），
**具体怎么组织创作，留给卡**。

> 这条是洞察 5 的延伸：不但"调用拓扑"是玩法，**"创作流程"也是玩法的一部分**。

## 四、图执行器与卡的格式

### 「图执行器」是什么（写给非程序员）

**图** = 一张"谁在什么时候被调用"的关系图：

```
        ┌─► 时间 agent ─┐
输入 ───┼─► 战斗 agent ─┼─► 主 agent（汇总·校对）─► 输出
        └─► 角色 agent ─┘
                ▲            │
                └──(条件)────┘      ← 条件分支
```

**执行器** = 照着这张图跑的程序。**它的全部职责：**

| 职责 | 具体表现 |
| --- | --- |
| 按图发起调用 | 把该给的数据给对应的 agent |
| **判断走哪条路** | 依据作者写死的条件**跳过**节点 —— 典型是**存在性判断**（"这个角色不在场 → 不调他"） |
| 并行 | 三个 NPC 互不依赖 → 同时发请求，而不是排队 |
| 循环 | 作者在图上声明循环几次，执行器照着做（**次数是写死的**） |
| 汇总 | 收集各 agent 的结果给主 agent |
| 兜底 | 静态校验（图里有没有环）+ 单轮调用硬顶（防坏卡烧额度） |

**它明确不做的事**：不做探索、不判断"何时该停"、不参与创作、不算规则。
**图走完就是一轮结束**（决定 #16）。

> ⚠️ **2026-09-14 现状**：上面职责表里的**并行 / 循环 / 条件**都是**目标能力**。
> 示例卡（见下）先用**纯线性图**把它们全部搁置 —— 机制留着，当前不实现。

**没有执行器会怎样**：那些"先调谁、什么条件下跳过谁"的逻辑，
就得散落在每个 agent 的提示词里各写一遍 —— 这正是"人格分裂"失败的一部分原因。

**体积预期**：不是重型框架，就是**一张声明表 + 一两百行 JS**。

### 拓扑长什么样（示意）

```json
{
  "拓扑": [
    { "agent": "时间", "上下文": "全部" },
    { "agent": "在场角色", "上下文": "全部", "并行": true,
      "当": "角色.当前位置 == 当前场景" },
    { "agent": "战斗", "上下文": "全部",
      "当": "场景.处于冲突中" },
    { "agent": "大纲", "上下文": "全部" },
    { "主agent": "汇总 · 格式校验" }
  ]
}
```

> **关键：「写死拓扑」不等于「只能直线执行」** —— **条件本身就是拓扑的一部分**。
> 但**条件怎么写**还没定（它不是代码，见待定 1），
> **条件依赖的字段从哪来**也还没定（见待定 2）。

### 示例卡的默认图（2026-09-14 用户定，**线性 9 个节点**）

```text
玩家行动
   │
   ▼
⓪ 精神分析   读玩家的真实处境，定"这一轮往哪个方向模拟"
   ▼
① 故事链     维护现有的链 / 按需长出新链
   ▼
② 行动判定（roll_check 的位置）   成没成、代价是什么
   ▼
③ 故事大纲                        这一轮发生什么、演到哪儿停
   ▼
④ 时间                            过了多久
   ▼
⑤ 地图                            地点长什么样
   ▼
⑥ 角色                            角色是谁、什么状态
   ▼
⑦ 故事                            全部写成正文
   ▼
⑧ 主 agent                        汇总 · 校验 · 提交
```

**用户给的排序理由（原话要点）：**

| 顺序 | 理由 |
| --- | --- |
| **精神分析在判定之前** | 判定本身就是"体验"的一部分 —— 玩家累了就别让他这轮吃大亏，**这事得在"判成没成"之前定** |
| 判定在决策层最前 | *「rollcheck 肯定在最前面」* |
| 大纲在时间之前 | *「还记得媒介理论吗，玩家体验高于世界自洽性」* —— **先定"要发生什么"，再定"花了多久"** |
| 地图在角色之前 | *「玩家可能在新地点遇到新角色」* |
| **故事链在判定与大纲之前** | 判定和大纲都要知道"现在有哪些链、走到哪一步了"；精神分析定的是整轮的调子，所以还排在它前面 |

**这条顺序隐含的两个性质：**

1. **反馈环是单向的** `事件 → 时间`。
   这是有意的取舍：**让故事节拍驱动时间，而不是让时间划定故事。**
2. **时间在前、地图在后 ⇒ 时间判耗时用不到本轮新生成的地点信息**
   （玩家去一个还没生成的地方时，时间只能凭大纲和常识判）。
   好处是**地图随后生成，可以对齐时间的判定** —— 一句话：**时间定调，地图对齐**。

### ⭐ 图的权力结构：决策层 / 具体化层 / 校验层

**结构不是"平级分工"，而是三层**：

| 层 | 节点 | 干什么 | 输出性质 |
| --- | --- | --- | --- |
| **决策层** | ⓪ 精神分析 · ① 故事链 · ② 行动判定 · ③ 大纲 | 决定**发生什么、往哪走** | 方向与情节 |
| **具体化层** | ④ 时间 · ⑤ 地图 · ⑥ 角色 · ⑦ 故事 | 把决策**变成具体的世界状态与文字** | 状态与正文 |
| **校验层** | ⑧ 主 | 一致性核对 · 格式 · 提交 | 合并结果 |

**三条规则：**

- **决策层内部没有"越权"一说** —— 大纲决定"遇到谁"就是它的职责
- **具体化层服从决策层**：角色 agent 不能推翻"该有个铁匠"，它只负责把铁匠长出来
- **决策层也不能违反已冻结的世界事实**（别让玩家遇到上一轮已经死掉的 NPC）——
  主要防线是决定 #11 的"上下文全敞开"（大纲看得到萨伦已经死了），主 agent 在校验层兜底

### ⭐⭐ 节点之间的数据流：公共部分 + 本轮上游累加（2026-09-14 用户问出来的）

用户原话：*「你得确认一下是不是每个节点都能拿到上一个节点的输出，
你那个『每个节点拿到的上下文完全一样』我没太看懂是不是这个意思。」*

**他的直觉是对的 —— 那句话是错的。** 而且当时它：

- **不在卡 JSON 里**，是**渲染器硬编码**的一段正文（md 本该是纯渲染产物）
- **当时的 `DESIGN.md` 里一次都没提过** —— 这条最要命：**九个节点的图，"数据怎么流"从来没写下来过**
- 还写着「**四块**设定」，而卡里早就是五块

**真正的约定**（现在写在卡的 `提示词.节点约定` 里）：

| 部分 | 内容 | 谁拿到 |
| --- | --- | --- |
| **公共部分** | 五块设定 + 核心剧本 + 全部历史 + 当前状态 + 玩家这一轮的原话 | **所有节点完全一样，顺序也一样** |
| **本轮上游** | 排在它前面的节点，**本轮**已经产出的结果 | **按拓扑顺序累加** |

```text
⓪ 公共
① 公共 + ⓪
② 公共 + ⓪①
③ 公共 + ⓪①②
…
⑧ 公共 + 全部
```

> ⭐ 一句话：**设定和历史人人有份，本轮的结论按顺序往前传。**

**为什么必须传** —— 卡自己的提示词就是证据（它们早就在互相引用了）：

| 节点 | 卡里的原话 | 读谁 |
| --- | --- | --- |
| ④ 时间 | 「大纲写『追了三天三夜』你就顺着判三天，那你就白拿工资了」 | **③** |
| ⑤ 地图 | 「把大纲『需要长出来』的东西，按生成器的原则长出来」 | **③** |
| ⑥ 角色 | 「精神分析会给一份『关系意向』名单……你照着执行」 | **⓪** |
| ⑦ 故事 | 「判定说成没成就是成没成，大纲说停在哪就停在哪」 | **②③⑤** |
| ⑧ 主 | 「大纲想让玩家遇到一个已经死掉的人 → 提示它换个人」 | **③** |

> ⚠️ 注意 **⑥ 读的是 ⓪（隔了六个节点）** ——
> 所以不能只传「上一个节点的输出」，**必须传「前面全部」**。
> 这条要是做错，⑥ 就永远收不到「关系意向」名单，主要角色永远升不了级。

**成本**：上游输出都是短 JSON（每个几百字符）。9 个节点累计多读约 36 份 → 一轮多几千字符。
跟每轮 7,353 的固定开销（五块 4,704 + 九个节点提示词 2,649）比，可以接受。

> ✅ **决定（用户 2026-09-14 下午）：`节点约定` 也进上下文**，不剥成"只给引擎"。
> 用户理由：*「节点 agent 也得知道自己和其他人是什么关系。」*
>
> —— 它不只是引擎的实现说明，也是**每个节点的自我定位**：
> 「我是第几个」「我拿得到什么」「我拿不到什么」。
> 加进上下文后，每轮固定开销 **7,835** 字符（4,704 + 2,649 + 482）。
>
> ⚠️ card/2 起，逐节点的上游清单不写进卡：卡里只有那条规则，清单由渲染器从拓扑现推（决定 #40）。

**一条纪律：拿不到的就别猜。**
宁可写「还不确定」，也别自己编一个上游结论 ——
那是**幻觉唯一能污染全局的入口**（因为下游会把它当真）。

**顺带修掉的**：
- 渲染器里那段硬编码正文删了 → 改成渲染卡里的 `节点约定`
- 「五块」「9 节点」这类**数字**改成从 JSON 数出来，不再手写
- 校验器新增「节点约定」一组检查：写死的「N 块设定」必须跟 `提示词.设定` 的块数对得上（逐节点上游不查 —— 它不写进卡，由拓扑推，见决定 #40）

### ⭐ 第 9 个节点：「故事链」（2026-09-14 加）

**它跟「地图 agent」完全同构：**

| | 维护什么 | 按需生成什么 |
| --- | --- | --- |
| 地图 agent | 区域 / 地点 / 谁在哪 | **新地点** |
| **故事链 agent** | 现有的链 | **新链** |

**为什么需要它**（用户 2026-09-14）：

> *「玩家完全可以不去探索地牢，坐两天马车去皇城，找个大户人家做管家，
> 然后和大小姐谈恋爱……（1）游戏保留这个自由度，（2）如果玩家真的这么做了，
> 要给他生成和将军公主这个故事相似的**其它完整故事链**，让他有事可做。」*

**为什么不做成地图 agent 的一个生成器** —— **单轮输出能力有限**：
地图 agent 的提示词已经有「空间维护 + 谁在哪 + 四条生成器原则」，
再塞进「生成完整剧情链（三层真相 + 线索 + 阶段 + 终点）」，
那正是「人格分裂技术」失败的重演。**独立节点，提示词只干一件事。**

**为什么它不需要"条件触发"**：它**每轮都跑**，但**大多数轮是空转的**
（玩家所在的地方已有活跃的链 → 输出空补丁）。
**用"常空转"代替一个我们还没做的条件机制** —— 这跟精神分析的「画像补丁」是同一个套路。

> ⭐ **推论：卡里有「两种生成器」**
> 一种产**空间与人物**（地图 / 角色），一种产**剧情骨架**（故事链）。
> 两者结构相同（维护 + 按需生成），但**内容的层级不同** —— 所以是两个节点。

### 工作副本 → 提交：一轮是一个事务

**一轮里所有节点读写的都是「工作副本」（内存，本轮有效）；只有最后一次「提交」才写权威状态（存档）。**
两个状态在「谁能读、谁能写、轮末怎么处理」上的区别见第三节「洞察 4」，这里只记它为什么不可省：

**为什么这是必须的 —— 它是失败路径的唯一防线：**

> 如果 ⑤ 地图 直接写权威状态，而 ⑦ 故事 那一步报错，
> **世界就更新了一半**：时间跳了、地图多了一层，玩家却没看到任何剧情；
> 刷新退回去，下一轮成功时再把"半个回合"一起持久化。

**主 agent 产出合并后的结果，真正的写入由引擎执行。**

> ⚠️ 这条同时是 `doc/CHANGELOG.md`（v0.5.4「加固 · 已知未修」）里
> 「失败/取消路径的内存与存档分叉」那个缺陷的正解 ——
> 那一处的根因正是"回合开头就改内存、`save()` 在末尾"，缺的就是这道闸。

> 💡 **写冲突的防线**：中途写的都是工作副本，"谁能改权威状态"只有一条路（提交），
> 所以不需要锁机制 —— 冲突只会发生在"同一个字段被两个节点都改了"，
> 由**主 agent 合并**时解决（合并规则本身是待定问题 5）。

> ✅ **阶段 4 已落地**：边界就在组合根 `src/stores/turn.ts` 的 `runTurnAction` 里
> —— 拷副本 → 跑 → 提交（一次写回）→ 落盘，失败 / 取消丢弃。落地方式与代价
> （叙事改为**整轮一起**显示，不再是每步实时出现）见决定 #39。

### ⭐ 精神分析在最前面（用户 2026-09-14）

> 💡 **由此得到一个值得记住的形状：这张图的第一个节点是玩家，最后一个节点是给玩家看的文字。**
> 首尾都是媒介 —— 中间那些世界状态，全是手段。
> 这与第一节「以玩家为中心的交互媒介」是同一条线的两端。

- 精神分析读的是**玩家在世界之外的真实处境**（第六节"外部身份"），
  以及**玩家怎么写的这句话**（措辞、情绪 —— 输入这个动作本身是体验的一部分）
- 它输出的是**方向**，不是世界状态 —— 它不写地图、不改 HP
- **它唯一能写的是「玩家画像」** —— 关于玩家自己的那份隐藏状态（见下）
- 玩家看不到它（第六节已定：不告诉玩家）
- 每轮都调用，这样它能跟踪玩家情绪的变化 —— 这正是它"自适应"的地方

#### ⭐ 它是「玩家建模」，用现成的学术框架（2026-09-14）

**不自己现编维度** —— 玩家研究这块的文献很厚，
**点名框架就等于借用模型读过的全部相关材料**：

| 维度 | 用什么 | 决定什么 |
| --- | --- | --- |
| **人口学** | —— | 年龄 / 职业 / 经济 / 感情 / 居住 → **他想看什么内容** |
| **动机** | **Bartle 玩家类型**（1996）：探索型 / 社交型 / 成就型 / 竞争型 | **该给他什么** |
| **心理需求** | **自我决定论（Deci & Ryan）**：自主 / 胜任 / 关系 | **该怎么给** |
| **当下** | —— | 心情、精力、还剩多少时间 |

> ⭐ **「点名框架」是个可以反复用的手法**：一个学术名词，省掉十行解释 ——
> 写「用 Bartle 分类」，模型就调出它知道的关于探索型玩家的一切；
> 写「SDT 的自主需求高」，它就知道该多给选择而不是多给奖励。
>
> **SDT 那一层最可操作**：自主高 → 多给选择；胜任高 → 难度卡在"够得着，但要使劲"；
> 关系高 → 多给能说话的活人。

**画像会越玩越准**：卡里给的初值只是作者的假设，之后每轮由精神分析补充
（它输出 `画像补丁`，**只在有新信息时才写** —— 每轮重写整份会让画像飘）。

> ✅ **循环：当前不做。**
>
> - 「这一轮走多远」由**大纲 agent 用自然语言**表达 —— 这是决定 #14 的直接推论
> - 线性图的成本上限天然 = `节点数 × 1`，本来就可预测，不需要循环来兜底
> - 同理，**扇出**（场景里 3 个 NPC 各调一次角色 agent）也先不做
>
> | | 大纲 | 循环 |
> | --- | --- | --- |
> | 表达什么 | **叙事跨度**（演到哪儿停） | **机械重复**（这个节点调 N 次） |
> | 怎么写 | 自然语言 | 声明式（次数写死） |
> | 现状 | ✅ 已有 | ❌ **不需要** |
>

> ⚠️ **一个要盯着的退化风险：时间 agent 会不会变成给大纲盖章？**
> 大纲如果写出"你追了三天三夜"，时间 agent 顺着判 3 天 —— 那它就退化成橡皮图章了。
> 它真正该做的是**把大纲的模糊节拍翻译成具体时长，并保持世界的时间一致性**
> （"三天三夜"要跟地图距离、NPC 作息、天色对得上）。这条要写进它的提示词。

### ⚠️ 硬约束：卡必须是**声明式**格式（JSON / YAML），不能是代码

理由：**用户是代码小白 —— 而他的用户多半也是。**
如果做卡要写 JavaScript，那 99% 的人做不了卡，"既能做卡"就废了，
**产品目标 ②（让强作者脱颖而出）也无从谈起**。

声明式的好处：作者改的是文字和数据；我们能校验格式；将来能加图形编辑器。

```json
{
  "agents": {
    "战斗": {
      "提示词": "你负责判定战斗的成败与伤情…",
      "写": ["伤势", "背包"],
      "输出格式": { "命中": "bool", "损伤": "string", "部位": "string" }
    }
  },
  "拓扑": [ "…" ]
}
```

> ⚠️ **2026-09-14 更新**：示例里不再出现 HP（已改为"伤势"），也**没有"读"字段** ——
> 上下文默认全敞开（决定 #11），不必逐个声明读什么。

### 卡的元信息：三种读者，三块（2026-09-14）

同一样东西被三种角色读，**别把它们混成一块**：

| 谁读 | 里面是什么 | 编辑方式（将来做卡界面时） |
| --- | --- | --- |
| **引擎** | 卡 ID · 卡版本 · 适配游戏版本 | 短字段 → 输入框 |
| **玩家** | 卡名 · 一句话简介 | 短文本 |
| **AI** | **世界设定** | **长文本** → textarea（拼进每个节点的提示词） |

#### ⭐「世界设定」是自然语言，不是变量字段

它跟各个节点的提示词是**同一类东西** —— 都是「作者控制 AI 的代码」。
所以它该长成提示词的样子，而不是一张配置表。

| 为什么不做成字段 | |
| --- | --- |
| **字段名永远不够用** | 「有没有神」「种族关系」「科技水平」「死人会不会变成鬼」…… 列不完，列完了就是又一份要维护的 schema |
| **光有标签没有信息量** | 只写「中魔」两个字，模型什么也没学到 —— **每个模型对"中魔"的理解都不一样**；有用的是一段解释 |

**它在图里的位置：每个节点的上下文，都以它开头。**
相当于一个「不用调用、但每个节点都能读到的第 −1 号节点」。

> ⚠️ 举例：「中魔」必须写成解释 ——
> *「魔法真实存在，也有靠它吃饭的人，但它是**专业技艺**，不是日用品。」*
> 不写清楚，模型的**高魔 D&D 先验**会自己往那个方向加料。

**但有两样东西不能塞进世界设定**（它们是引擎字段）：

| 字段 | 为什么归引擎 |
| --- | --- |
| **历法** | `src/utils/calendar.ts` 要照它算日期、`format()` 要照它排版 —— 它是**开关**，不是说明 |
| **起始时刻** | 开局就要用（**两种**写法：具体时刻 / `now`） |

> 有意思的是「我们用现实历」这句**两处都要出现**，但角色不同：
> 引擎那份是 `"历法": "real"`（一个值），世界设定那份是给模型的**说明**
> （"用的是现实历，有星期、有月份、有四季"）—— 后者让模型知道该怎么写季节和节气。

### 卡的标识与碰撞（2026-09-14）

**卡 ID 是给机器认的，卡名是给人认的。** 分开，是因为人的名字会改、会重复、会带空格标点。

**ID 干三件事：**

| # | 干什么 | 不这么干的后果 |
| --- | --- | --- |
| ① | **存档认亲** —— 存档里存的是世界状态，得记「这是哪张卡的状态」 | 打开存档时不知道该往哪个世界里装 |
| ② | **导入时判断「同一张还是两张」** —— 决定覆盖还是并存 | 只能靠文件名猜，而文件名可以随手改 |
| ③ | **版本迁移的锚**（待做）—— 卡格式变了要迁移，得有个稳定的东西指着它 | — |

#### 怎么防重复？—— 防不住，但要「重复了也不出事」

**这个项目纯前端、没有服务器、没有注册表可查重。**
所以目标不是防重复，是**让碰撞可检测**。三道防线：

| 防线 | 干什么 |
| --- | --- |
| ① **命名空间** | ID 形如 `作者名.卡名`（`me-aqua.morningwind`）—— 把「卡名撞」降级成「作者名撞」 |
| ② **导入时绝不静默覆盖** | 撞了就提示，或自动改名并存 → **本机永远不会有同 ID 的两张卡** |
| ③ **存档核对（真正的保险）** | 存档里记 **卡 ID + 卡名 + 卡版本**，打开时核对 |

> ⭐ **③ 才是关键**：碰撞的**全部危害**都集中在「存档装进错误的世界」。
> **只要检测得出来，碰撞就只是个小麻烦，不是灾难。**

**命名空间的负担是零**：编辑器第一次打开问一句「你叫什么」，之后**所有卡自动带前缀**，
作者永远不用为每张卡想前缀。（顺便白送：分享出去的卡能看出是谁做的。）

**ID 规范**：小写字母 / 数字 / 连字符，无空格；用**点**做命名空间分隔
（不用斜杠 —— 点在 Windows 文件名里合法，万一将来想拿 ID 当文件名）。

**导入时看三个字段的组合：**

| 卡 ID | 卡名 | 提示 |
| --- | --- | --- |
| 相同 | 相同 | 「这是《X》的**新版本**（0.1.0 → 0.2.0），要升级吗？」 |
| 相同 | **不同** | 「**ID 撞了**：你已有的叫《X》，这张叫《Y》。要并存吗？」→ 自动改名 |
| 不同 | 任意 | 直接导入 |

> ⚠️ 只比对 ID 会误判成「升级」，然后**悄悄把地牢卡覆盖成恋爱卡** ——
> ID + 卡名一起看，才给得出人话提示。

### 卡的存储格式：JSON（2026-09-14 定）

理由只有一条，但它决定性地结束了这个纠结：

> **作者不手写卡文件。** 将来会有「做卡界面」，作者在 textarea 里写提示词，
> 多行、不用转义、不用管引号 —— **他永远看不到那个 JSON**。

所以格式该为**引擎**优化，而不是为手感服务：

| 为什么选 JSON | |
| --- | --- |
| **零依赖** | 浏览器原生 `JSON.parse` / `JSON.stringify`，不用引解析器 |
| **`git diff` 干净** | 提示词**按行存**（字符串数组），改一行只显示一行 |
| **表达力够** | 卡里有树（区域 → 地点）、有表（状态字段），JSON 天然表达得了 |

**一张卡 = 一个自包含的 `.json` 文件。** 导出 → 别人导入 → 玩，
这就是「既能做卡又能玩卡」的闭环。

> 📌 **做卡界面以后再做**（2026-09-14 定：先搭最基础能跑通的卡 + 引擎）。
> 但它既然已经定了，卡的格式就不用再为「作者手写舒不舒服」妥协了。

### 显示层（界面由卡驱动）

决定 #15 带出了一个之前没讨论过的层：**界面由卡驱动**。

现在的界面是**写死**的（时间 / 地点 · 回合、故事区、输入框都是固定布局）。
将来卡的声明里要包含"显示什么"：

| 卡的类型 | 侧边栏可能显示 |
| --- | --- |
| 恋爱模拟 | 好感度 · 心情 · 关系网 |
| 侦探推理 | 剩余时间 · 线索清单 · 嫌疑人 |
| 生存恐怖 | HP · 感染度 · 物资 · 理智值 |

**用户 2026-09-13 的判断（我认同）**：

> 「我们的游戏是 RPG 基调的，我感觉大差不差咯，时间地点角色物品嘛，
> 没事等后面我们开始做**范例游戏卡**的时候这些东西很快就能定了，现在干想也想不出来。」

**默认集合锚定 RPG 四要素（时间 / 地点 / 角色 / 物品）** —— 落到示例卡就是下面这套布局。

**示例卡的布局（2026-09-14 定）**

```text
┌──────────────────────────────────┬───────────────┐
│ 顶栏：时间 · 当前场景             │ 侧栏           │
├──────────────────────────────────┤  · 地图        │
│                                  │  · 角色        │
│           故事正文                │  · 背包        │
│                                  │               │
├──────────────────────────────────┤               │
│ 输入框                            │               │
└──────────────────────────────────┴───────────────┘
```

**四个区域**：**右侧栏** · 顶栏 · 中区（故事）· 底部（输入框）。
**侧栏一通到底**（占满整个**右侧**高度），左侧三个上下叠。

> 📌 **左右对调过**（用户 2026-09-14：*「左右换一下更好，我感觉」*）——
> 侧栏从左边挪到了右边，故事区留在左侧。
**侧栏要很大** —— 它要装三块上下叠的内容：

| 区块 | 放什么 |
| --- | --- |
| **顶栏** | 时间 · 当前场景 |
| **侧栏 · 地图** | 区域 / 地点的结构。**不在当前场景的角色只在这里留一行「名字 + 身份」** |
| **侧栏 · 角色** | **主控在前**，当前场景的其他角色在后（按下面的四段结构展开） |
| **侧栏 · 背包** | 所有随身物品 —— **武器 / 防具 / 硬币 / 杂物全在里面，不单列装备与钱包** |
| **中区** | 故事正文 |
| **底部** | 输入框（玩家在这里行动） |

> 💡 **背包参考《逃离塔科夫》**（用户点的）：武器、卢布、美元都塞在同一个容器里。
> **但当前不做容量与负重** —— 那属于细节，范例卡里没必要。

> 💡 **一个可能的简化**（待验证）：显示层也许不需要单独声明 ——
> 它可以从**状态 schema 自动推导**（卡声明了"好感度"这个字段 → 侧边栏就显示它）。
> 这样作者只写一次，不用同时维护"状态"和"界面"两份声明。

仍待明确的边界（到那时再说）：
- 卡能不能控制**样式**（配色、布局），还是只有"放什么"？

## 五、世界结构：区域 / 地点 / 场景（2026-09-14）

> **来源**：三层地图由用户 2026-09-14 讲述（来自他之前项目的经验），职责定义与推论为讨论中补齐。
> **这是第一张示例卡（冒险者地牢）的地基，也是引擎要改的第一处。**

### 三层各是什么

| 层 | 职责 | 变化频率 | 用户的例子 |
| --- | --- | --- | --- |
| **区域** | **演算边界**（这轮模拟哪些人）+ **移动代价的单位** | 极少变 | 学校 |
| **地点** | **存在性判断的粒度** + **持久化单位** | 偶尔变 | 教学楼 |
| **场景** | **叙事舞台**（这轮镜头对准哪） | 每轮变 | 高二3班门口 |

**用户原话**：*「每轮游戏只需要演算当前区域发生的事情（只关心学校，不关心我妹妹在家里做什么），
玩家在区域之间移动需要花时间。」*

→ **区域 = 模拟的 LOD（细节层次）** —— 这是控制上下文规模的核心开关。

### 地点不是"没用的中间层"

> 你在地牢第 2 层打怪，队友在营地等你。队友**不在场景里**，但他**存在**。
> 只有「区域 + 场景」两级的话：要么把他硬塞进当前场景（错），要么他凭空消失（也错）。

- 地点是三层里**唯一稳定**的：场景每轮都换，地点能连着好几轮不动
- **据此修正决定 #10 的措辞**：**在不在当前区域** → 决定角色 agent 这轮**要不要被调用**；
  **在不在当前场景** → 决定他**在不在镜头里**（在营地等你的队友，这轮不写他，但他没消失）

### ⭐ 地图 = AI 生成结果的**缓存**

| | 输出性质 | 时效 |
| --- | --- | --- |
| 故事 agent | 叙事 | **流** —— 演完就过去了 |
| 地图 agent | 地图增改 | **事实** —— 写进去就冻结，之后谁都不能改 |

**规矩：生成一次就冻结。** 挡的是「AI 每回合现编 → 世界漂移」
（这回合旅店在广场东边，下回合 AI 忘了，编到西边去）。

### ⭐⭐ 生成器：卡里的一等公民

用户 2026-09-14 的原则（原话大意）：

> **卡作者可以随便做预设，但 AI 要有完整的生成能力。**
> 「生成小镇」和「标准化生成新区域 / 新地点」是**两件不同的事情**、
> **两套不同的提示词** —— 而且**这两套提示词都是卡作者写的**。

**生成器** = `{ 适用（管哪块地方）+ 原则（提示词）+ 输出（地图增改）}`

- 一张卡可以声明 N 个生成器：`生成小镇`、`生成地牢新层`、`生成随机遭遇`……
- 匹配顺序：**具体 > 通用** —— 有针对性规则就用它，没有才落回通用生成器
- 用户给的通用原则示例（**由作者写进卡里**）：
  > 在地牢生成新的层时：（1）有主题，比如雨林、火山、冰冻、魔瘴
  > （2）有一条或者几条前进路线，有明确的前往下一层的方式
  > （3）有敌意单位、中立单位和友善单位，确保事件多样化而有挑战性

> 💡 **推论：卡的完整度不再是"游戏能不能玩"的前提。**
> 作者写一半也能跑 —— 剩下的由 AI 长出来。这是"新手能用预设、高手能写精细图"的落地方式。

#### ⭐⭐ 统一模式：**卡给的是「种子」，不是「边界」**（2026-09-14）

这个模式在《晨风镇》里**已经出现五次了**：

| 东西 | 作者给的 | AI 能长出来的 |
| --- | --- | --- |
| **区域** | 三个（晨风镇 / 镇郊 / 地牢） | **新地点** |
| **故事链** | 「将军与公主」一条 | **新链**（玩家跑去皇城，就长一条） |
| **种族** | 见过的五个 | **新族类** |
| **生成器** | 原则 | 具体内容 |
| **常见物** | **8 栏共 228 条**，每栏十几到五十几条不等（食物 24 / 衣物 40 / 武器与防具 24 / 药材 16 / 魔法材料 16 / 职业 32 / 日常杂物 24 / 女人家的东西 52） | **别的东西** —— 需要就随手加 |

> 💡 **「常见物」这一格（2026-09-14 用户提出）解决的是一个很实际的问题**：
> 没有它，模型会按**它自己的奇幻默认值**写 —— 面包、麦酒、长剑、皮甲。
> **有了它，世界才有「晨风镇的味道」**：腌鱼、绑腿布、伐木斧、老祭司的草。
>
> 而且这份列表**尽量咬住已经定下的东西**，不是随便凑的：
> 边陲小镇 → 腌鱼和咸肉；商队补给 → 盐和熏肉是"好东西"；
> **「铁头棍 —— 打昏比打死容易」** 咬住打昏规则；
> **「老祭司的草 —— 他不说是什么」** 咬住"神不存在、但他从不纠正这个误会"。

#### ⭐⭐ 顺带一条手法：**词表是最强的风格引导**（2026-09-14 用户提出）

> 用户原话：*「在衣物和武器防具这一块你要**往适合年轻女性的方向写**，
> 这样 AI 也会更愿意生成年轻女性角色 ——
> **因为他拿到的提示词里全都是相关的东西**。」*

**光在叙事风格里写「值得记住的大多是年轻女人」，是抽象的、一句话。**
**而「常见物」列表是具体的、每一轮都出现的 228 条词。**

> ⭐ **你想让模型产出什么，就先让它的上下文里充满那个东西。**

所以《晨风镇》的衣物和武器防具两栏**有意偏向年轻女性**：

| 栏 | 现在写的 |
| --- | --- |
| **衣物** | 亚麻长裙 · 束腰罩衫 · 羊毛披肩 · 高领薄衫 · 及膝衬裙 · 绑带短靴 · 发带 …… |
| **武器防具** | 细剑 · 轻便猎弓 · 皮护腕 · 皮甲 · 贴身软甲 ……（换掉了「伐木斧」「长矛」） |

**这不是"改个措辞"，是换掉了模型每一轮都要读一遍的那批词。**

> 💡 **它跟「例子 > 规则」是同一条原理的两端：**
> - 那条说的是**怎么写**（给例子，别给规则）
> - 这条说的是**写什么**（你想让什么出现，就往上下文里堆什么）

**用户 2026-09-14 的原话（第四次那次）：**

> *「种族也不是写死的，**魅魔蜥蜴人奇美拉史莱姆娘天使**这种东西，
> 如果 AI 觉得有必要他就**随手加**就行了。」*

> ⭐ **一句话概括：作者写「语法」，AI 生成「句子」。**
>
> 这不是"作者偷懒"，而是**卡格式的设计原则** ——
> **凡是"给一个封闭清单"的地方，都该改成"给一批种子 + 一句边界"。**
> 清单会过时、会长不全、会挡住玩家；**种子不会**。

> ⚠️ **但它有代价，必须配一条边界**：
> 开放不等于随便 —— 用户同时给了约束：*「只要符合这个世界的调子」*
> （中魔、边陲、大部分人一辈子没出过雾岭）。
>
> **种子开放 + 调子封闭，两者缺一不可。** 只开不放，卡会僵；只放不封，世界会散。

### 移动耗时：全部交给时间 agent（用户 2026-09-14）

**引擎里没有任何"跨区域 = X 小时"的规则，一行都没有。**

- 地点**会**有描述，但**不保证**写了距离或耗时
  （地牢入口的描述可能有一句"离小镇边缘两公里，徒步半小时"，**也可能什么都没有**）
- **每回合**都由时间 agent 根据它掌握的全部信息重新评估时间演化
- 时间 agent 提示词里只有**倾向**，没有硬规则：
  > 「通常跨区域移动要花比较长的时间，比如以小时记，而跨地点移动花的时间就比较短，
  > 可能只有几分钟，请你综合判断……」

**原则：描述里的量是「基准」，不是「常量」。**

- 偏离基准**允许**，但**必须给出理由** —— 而那个理由就是本回合的新内容
  （用户自己说的"半路肯定出事了"就是这条）
- 这是**提示词层的规矩**，引擎不参与

**由此得到一个区分（AI 补，待确认）：**

| 描述里的东西 | 性质 | 能不能变 |
| --- | --- | --- |
| **结构**：有没有 / 在哪 / 有几个 / 是什么 | 世界事实 | **冻结**（"生成一次就冻结"管的是这个） |
| **预期**：要多久 / 多难 / 多常见 / 一般怎样 | 基准值 | **可偏离，偏离即内容** |

### 离屏区域：惰性补算，不预演（用户 2026-09-14）

玩家在地牢里待了三天，小镇怎么办？**不预演。**

> 用户原话：*「等到玩家回到小镇，在渲染之前肯定要根据当前的世界状态（3 天后）
> 更新小镇的状态嘛，那时候把该算的都算一遍就行了。」*

→ 这是「只演算当前区域」的延伸：**离屏的东西不模拟，直到它重新入场。**
→ 中间过程不留，只留最终值。

> 💡 **AI 补（待确认）**：补算要**有根据** —— 优先更新"本来就在演化"的东西
> （商人进货、悬赏变化、各 NPC 的处境），**别凭空制造大事件**。
> 长跨度该有长跨度的变化，但那变化应当呼应已有的线索。

### NPC 位置：三级分辨率（用户 2026-09-14，来自他之前项目的做法）

**知道的细节随距离递减：**

| NPC 在哪 | 引擎 / agent 知道多少 |
| --- | --- |
| 在当前区域、不在当前地点 | 姓名 + **在哪个地点** |
| 在当前地点、不在当前场景 | + **在哪个场景** |
| **在当前场景** | + 服装、姿势、心情……**每回合都变** |

→ 这正是决定 #11 那条「实现建议」的**裁剪规则**。
→ 阶梯的**粗细应当是作者可配的**（恋爱模拟卡可能想让全镇人都记住好感度），雏形先用这套。

### ⭐ 「下楼的条件」：写结果，不写方式（2026-09-14）

用户明确：**玩家应该能绕过作者设想的路径。**

> 原话：*「我们也非常鼓励他从异世界召唤一个坦克过来用 125mm 贫铀穿甲弹把冰霜巨魔两炮轰死。」*

**这条直接决定了条件该怎么写：**

| 写法 | 例子 | 判定 |
| --- | --- | --- |
| ❌ **方式导向** | "击败霜牙巨魔" | 把玩家锁死在一条路径上 |
| ✅ **结果导向** | "霜牙巨魔不再挡着那条路" | 死了 / 跑了 / 被引走了 / 被坦克轰了，都算 |

→ 与「传统规则表为什么会死」是同一个病：**条件一旦绑定实现方式，自由度就死了。**

**同时注意：这件事和待定问题 1/2（拓扑里的「当」）不是一回事。**

| | 拓扑里的「当」 | 世界内的"能不能下楼" |
| --- | --- | --- |
| 是什么 | **要不要调用某个 agent** | **世界内的事实判断** |
| 谁判 | 引擎（按作者声明的条件） | agent（按常识 + 地图事实） |
| 现状 | 待定问题 1/2，**当前不做** | **不需要任何新机制** |

### ⭐ 新 agent：「行动判定」（用户 2026-09-14，从旧项目带来）

用户旧设计里有一个**专职判定玩家行动成败的 agent**，本轮确认带进新架构：

```
玩家行动 ──► 【行动判定 agent】──► 故事大纲 ──► 故事
               （成功 / 失败 / 代价）
```

**两个值得记下来的性质：**

1. **它就是 `roll_check` 的转世** —— 从"引擎掷骰"变成"agent 裁量"。
   `doc/CHANGELOG.md` 记着 `roll_check` 已删、成败交给模型：现在"这一步由谁做"有答案了。
   第十一节那张表里的「判定 | 单模型顺手判 | 专职 agent 判断」由此**具名**。
2. **判定先于叙事，是为了防止"故事需要它成功"污染"它到底成没成"。**
   判定与写故事若在同一个 agent 里，模型会本能地让玩家总赢；
   分开调用后，判定没有"为了让故事好看"的压力。

> 💡 「异世界召唤坦克」正好是这个 agent 的压力测试：它得判"这个行动在这个世界里成立吗"。
> 而**世界的物理法则写在卡作者的提示词里**（低魔 / 中魔 / 高魔 / 现代混入），
> 判定 agent 据此裁量 —— 这又是「提示词即代码」的一次落地。

## 六、玩家（角色扮演的根基）

> **本节原为"玩家与开局"的缺口补写，2026-09-13 用户回答了关键问题后基本成型。**
> 总纲见第一节「**角色扮演是根基**」。

### ⭐ 玩家 / 主控：两个不同的东西（用户 2026-09-14 定的术语）

> 用户原话：*「你得区分好玩家和主控，**玩家是坐在电脑前的人，主控才是打怪升级招队友的人**。」*

| | **玩家** | **主控** |
| --- | --- | --- |
| 是谁 | **坐在电脑前的那个人** | 世界里的那个角色（打怪、升级、招队友的那个） |
| 在哪 | **世界之外** | **世界之内** |
| 有什么状态 | **外部身份**（「男大学生，在宿舍，想放松」）—— **隐藏** | 游戏内状态（六项属性、伤势、背包、位置）—— **显示** |
| 谁读它 | **⓪ 精神分析**（见第四节默认图） | 行动判定 / 地图 / 角色 / 故事 |
| 玩家看得见吗 | ❌ 不显示 | ✅ 要显示（RPG 基调，属显示层） |

**这个区分一次性解决三件事：**

1. **"玩家在世界之内"这句自相矛盾的话有了正确写法** —— 在世界之内的是**主控**（第一节已同步修正）
2. **代入感的来源说清楚了**：玩家在世界之外 → 通过**主控**进入世界 → **"输入这个动作"就是那道桥**
3. **待定问题 8 有答案了**：**主控**就是世界里的一个普通角色，走同一套状态机制；
   **玩家根本不是角色** —— 它是被模拟的对象（精神分析读的那份隐藏状态）

> 💡 **外部身份不显示，但照常参与模拟** —— 它是"隐藏状态"。
> 这也解释了「精神分析」的定位：它读的是**玩家**，影响的是模拟方向，
> 而玩家不会看到"系统在分析我"。

> 📌 **两句用户原话（2026-09-13）**：游戏内状态「**玩家状态当然要显示啦**」；
> 外部身份「**由这个游戏进程本身维护**」，而且「**不告诉**」玩家。
> 所以外部身份是游戏进程持有的**隐藏状态** —— 它照常参与每轮模拟，只是不显示。

### 行动怎么进图

| 维度 | 结论 |
| --- | --- |
| **根节点输入** | 与**上一回合的输出**（游戏历史记录 + 世界最终状态）一起进入 |
| **输入这个动作的意义** | 玩家坐在电脑前输入命令，**这个动作本身就是沉浸化的体验** —— 不能降格成调参 |
| **谁在执行** | 输入的是**玩家**；被模拟、被判定、被写进故事的是**主控** |

```text
上一回合的输出 ──┐
（历史 + 世界最终状态）├──► 【根节点输入】──► 各节点 ──► 新的状态与叙事
玩家本回合的行动 ──┘
```

### ⭐⭐ 主控有多强，是「卡」说了算（2026-09-14）

**引擎不规定主控的战斗力 —— 那是卡的设定。**

《晨风镇》这张卡的选择是：**主控是个能代入的普通人**。用户原话：

> *「因为玩家是电脑前的真人，为了沉浸感，我不想让主控的战斗力太突破常识，
> 连火球术我都不太想让主控学，**他应该始终是一个能代入的普通人**。
> 但其它卡作者可能有不同的想法，**这只是我对现在这个预制卡的想法**。」*

**为什么这条值得单独记 —— 它一次性解释了好几个之前分散的决定：**

| 之前的决定 | 在这条底下才说得通 |
| --- | --- |
| **中魔世界**（2026-09-14 由"低魔"改档） | 世界里**有**法师 —— 但**主控不是**。别因为世界有魔法就顺手给他魔法 |
| 没有等级 | 等级会让主控"越打越不像人" |
| 属性 1–10 | 那是普通人的量程 |
| 属性描述"你是什么样的"，不是"你有多强" | 同一条思路 |

> ⚠️ **它不是引擎规则。** 别的作者完全可以做一张「玩家是龙傲天」的卡 ——
> 引擎只提供机制（状态 / 判定 / 生成器），**"主控有多强"永远由作者写**。
> 这与第一节「控制权归作者」是同一条线。

**队友不受这条限制**：队友可以比主控强（龙族队友能顶几个成年人），
但**不能让他一个人杀穿** —— 他得是"一个有用的人"，不是替玩家通关的钥匙。

#### 同理，「谁会死」也是卡说了算

**引擎不规定终局。** 《晨风镇》的选择是：

| 谁 | 能死吗 |
| --- | --- |
| 主控 · 关键角色（**有名字的**） | ❌ **绝不** |
| 地牢里的怪 | ✅ 可以死，**也可以被打昏** |
| **世界本身** | ✅ 会变（政变推进、公主被转移），**但不会走到"这局白玩"** |

**用户的理由（2026-09-14）**：

> *「毕竟我们的游戏是**线性叙事没有回档的选项**，
> 关键角色的死亡是个**巨大的 discourage**。」*

⭐ **这条理由比"不死"本身更重要** —— 它一次解释了三件事：

> **线性 + 不能回档 ⇒ 不可逆的失去 = 玩家的巨大挫败。**

而「**打昏**」之所以被单独点出来，是因为它**比杀死更好用**：
被打昏的人可以审问、可以绕过、可以放走、可以在醒来之后变成仇人或者朋友。
**下杀手永远只是选项之一，不是唯一解法。**

执行者是**大纲节点**；判定节点可以判出"这一击很致命"，
但那一击要落成**重伤 / 被俘 / 打昏 / 失去什么**。

别的卡可以做别的选择 —— 让主控死、做成 Roguelike 换人重开、或者死后进另一个世界。
**这件事跟"主控有多强"一样，永远归作者。**

### ⭐ 没有等级系统（用户 2026-09-14 定）

> 用户原话：*「我倾向于没有，玩家可以有 HP 和攻击，他可以做一些事情提高这些数值，
> 但**不需要有一个专门的等级来告诉他自己变强了**，他得**通过自己亲眼看到的游戏故事**
> 来决定自己能不能打过冰霜巨魔。」*

**所以：主控的状态里有一堆具体的东西（六项属性、伤势、背包），但没有"等级"。**

**为什么这条比看起来重要 —— 等级是数值规则的天然入口：**

| 描述方式 | 能不能被公式化 |
| --- | --- |
| 「你的剑更利了、胳膊上多了道疤、这次那一爪你扛住了」 | ❌ 写不成公式 |
| 「你 3 级，怪 5 级，打不过」 | ✅ **天生就是拿来比较和计算的** —— 一写就是规则表 |

等级是一个**抽象进度条**：它不描述世界里的任何具体东西，
唯一的作用就是"告诉玩家你变强了" —— 而这件事**应该由故事来告诉他**。

**用户给的解法（2026-09-14 追加）：不要"攻击力"这个汇总值，改用多维度的属性。**

参考 **《辐射》的 SPECIAL**（力量 / 感知 / 耐力 / 魅力 / 智力 / 敏捷 / 幸运）：

> 用户原话：*「还是需要一些数字的，但不一定叫攻击力，你知道辐射吧，
> 里面把人的能力分成 special 七个，什么力量敏捷之类的，
> **一次攻击的效果是由这些数字综合决定的**，可以参考这个。」*

#### 示例卡的最终属性集（用户 2026-09-14 定，**6 项**）

从 SPECIAL 七项**砍到六项，全部二字名**：

| 属性 | 它管什么（**要写进卡的提示词**） |
| --- | --- |
| **力量** | 扛、推、砸、近身硬碰 |
| **敏捷** | 躲、跑、跳、反应快慢 |
| **技巧** | 精细的手上活：开锁、扒窃、包扎、弓弩准头、剑术的细腻处 |
| **魔法** | 感知魔力、施法、抵抗法术、与魔法物品共鸣 |
| **智力** | 记忆、推理、学识、看穿 |
| **魅力** | 说服、威慑、取信、谈判 |

> **顺序**：力量 · 敏捷 · 技巧 · 魔法 · 智力 · 魅力（用户 2026-09-14 定）。
>
> ⚠️ **「魔法」这个属性名有个坑要堵**：模型很可能把它读成**法力值 / MP**。
> 卡的提示词里要写死一句：**「魔法」是你与魔法亲和的程度，不是法力值，不会消耗。**

> 💡 **每个属性都必须带一句"它管什么"的定义。**
> 因为属性是**判定 agent 的判断依据** —— 定义不清（尤其"敏捷 vs 技巧"这种天生重叠的），
> 等于没有依据。

**被砍掉的两项及理由：**

| 砍掉 | 理由 |
| --- | --- |
| **幸运** | *「幸运在大多数游戏里是 roll 点用的，咱们没有这条」*（用户原话）—— **一针见血**：幸运是**掷骰系统的残留字段**。`roll_check` 已经删了（成败交给 agent 判断），再把幸运留在状态里，等于偷偷把随机性请回来 |
| **感知 / 耐力** | 用户未采纳（感知的部分职能并入「技巧」） |

#### ⚠️ 世界法则必须落进提示词 —— 而且要**写成例子**（2026-09-14）

> **同一天改过一次档**：早上定的是"低魔"，晚上改成**中魔** ——
> *「把低魔改成中魔，我觉得还是需要有治疗术的，但是施法条件比较苛刻，
> 比如资深魔法师才能熟练使用，或者必须要用上草药，而且只能加速愈合或者止疼，
> 不能凭空直接恢复。」*

**光写在设计文档里没用。** 模型的默认先验是**高魔 D&D**（法术满天飞、魔法物品遍地）——
「中魔」**离那个先验只差一步**，不写清楚边界，它会自己往"随手一挥"的方向跑。

**所以世界法则要写进两处：**

1. **生成器原则** —— 施法者罕见、魔法物品有来历、地牢里的魔法造物有来历
2. **判定 agent 的提示词** —— "这个世界的魔法是专业技艺，不是日用品"

这正是「提示词 = 作者控制 AI 的代码」的又一次落地。

##### ⭐⭐ 但要写成**例子**，不要只写规则（用户原话）

> *「你可以多写一些例子在里面 —— **根据之前的经验，模型比起规则更喜欢读例子然后仿写**。」*

**这条对整张卡都成立**，不只对魔法。它跟 `.agents/skills/verification` 里记着的那条教训（示例是模型的行为模板），是**同一件事的两个形态**：

| | 老形态（踩过的坑） | 今天这条 |
| --- | --- | --- |
| 教训 | **示例是模型的行为模板，说明只是注释** | 同上 |
| 用在哪 | **提示词**怎么写 | **卡的内容**怎么写 |
| 症状 | 给个占位符 → 模型学成留空 | 只写"中魔" → 模型按自己的先验自由发挥 |

**所以《晨风镇》的【治疗】是这么写的 —— 五条具体例子，而不是一条规则：**

> - 镇上唯一的药师会配一种黑乎乎的膏药。敷上三天，刀口就收口了 —— 疼，但管用。
> - 神殿的老祭司会一手"按手"：他按住伤口念一段话，血就止住了。镇上人都说那是女神显灵 ——
>   其实那是他年轻时跟军医学的止血手法，加一味嚼烂的草药。**他从来没纠正过这个误会。**
> - 酒馆二楼住着个退役军医，专治箭伤。他不念咒，只用刀、线和烈酒。收费比谁都贵 ——
>   因为救活的人比谁都多。
> - 三十里外塔里那位法师，据说能把断骨接上。代价是先付十枚金币，
>   而且他会让你睡过去，醒来时**已经过了三天**。

> 💡 **顺带一个副产品**：写【治疗】的时候发现，
> 「**没有一键回满**」跟「**没有 HP、只有伤势**」是**同一条设计的两面** ——
> 伤势之所以有意义，正因为它**不能凭空消失**。**治疗术只能加速，不能跳过。**

#### 这条为什么正好治"规则表"的病

**从「攻击力」换成六项属性，本质上是把「汇总值」拆成「维度」：**

| | 攻击力 12 | 力量 · 敏捷 · 技巧 · 魔法 · 智力 · 魅力 |
| --- | --- | --- |
| 是什么 | 一个**汇总后的强度** | 这个人**是什么样的** |
| 能不能直接比大小 | ✅ `12 > 8 → 我赢` | ❌ 说不了"我力量7敏捷3"和"他力量5敏捷6"谁强 —— **要看情境** |
| 结果什么时候产生 | 已经躺在字段里了 | **在判定 agent 的判断里综合产生** |

> ⭐ **由此得到一条可以反复用的原则：汇总发生在判断里，不发生在状态里。**
> 这与决定 #7（"中间状态不必保留，只存最终状态"）是同一个思路，
> 也与「引擎只**存**事实，不**算**事实」是同一条线。

**属性还有第二个用处：它是给「行动判定」agent 的判断依据。**
判定 agent 判"我翻过这堵墙"时，看的是敏捷与力量 ——
**而不是问"我的翻墙等级是多少"**。
属性描述能力的**维度**，让玩家能做的事变**宽**，而不是让数值变高。

#### 两条实现约束

1. **属性集由卡作者声明，引擎不认识 SPECIAL** ——
   引擎里不该出现"力量 / 敏捷"这些字。恋爱模拟卡可能声明「好感度 / 心情」，
   硬核生存卡可能声明「体力 / 理智」。
   （这正是"状态由作者定义"的直接应用，与决定 #12 一致。）
2. **属性是判断的输入，不是判定的公式** ——
   提示词里要挡住"力量 7 > 巨魔 5 → 我赢"这种算法。

> 💡 **与"数值可以有、公式不能有"是同一条线**：数值要对应世界里**具体的东西**
> （剑、体格、伤势），而不是一个抽象标签。
>
> ⚠️ **顺带解决了一个悬空问题**：「成长」不需要单独的 agent ——
> 成长不是一次判定，它就是**世界状态的改变**（背包 / 本事 / 伤势 / 经历），
> 落在**角色 agent** 那一个节点上。

#### ⭐ 「没有等级」之后，成长靠什么？—— 核心循环（2026-09-14 补完）

**用户把下地牢的动机从"救公主"改成"找东西"之后，循环自己闭上了：**

```text
下地牢 → 采到 / 打到东西 → 回镇卖给药师、铁匠、公会 → 换钱买装备 → 下得更深
```

| 谁 | 收什么 |
| --- | --- |
| 药师 | 石壁上的苔、地衣（药材原料） |
| 铁匠 | 旧时代的铁（回炉是好钢） |
| 公会 | 怪身上的东西（按件算钱） |

> ⭐ **这就是"没有等级的成长曲线"** —— 变强靠**装备和钱**，不靠数字。
> 它跟「没有等级」「没有经验值」「状态里只存具体的东西」完全咬合。
>
> 💡 **额外的好处**：每个 NPC 都有了**收东西的理由** ——
> 玩家走进铁匠铺，萨伦有话说。**NPC 的用处是从经济里长出来的，不是硬塞的。**

#### 顺带一条措辞纪律：**「作者没写」≠「世界里没人知道」**

地牢有几层 —— **这不是卡的空缺，是一个设定**：

> 用户原话：*「地牢七层的事就别提了，**没人知道地牢有几层**；
> 最深处有公主也只是公告里这么说了，大家才将信将疑的。」*

所以卡里写的是「**也没人知道它有多深**」，还配了一个细节：
酒馆墙上那排木牌，每块刻着一个名字和一个层数 —— **层数一个比一个大，真假没人说得清。**

> ⚠️ **这两种"不知道"写法完全不同：**
>
> | | 模型会怎么做 |
> | --- | --- |
> | **卡的空缺**（你没写） | 自己补一个 —— 而且多半是"七层"这种烂大街的默认值 |
> | **世界里的未知**（你写了"没人知道"） | **保持它未知**，还会拿它做文章 |
>
> **想让它别乱补，就得把"不知道"本身写成设定。**

### ⭐⭐ 状态里存事实，不存结论（2026-09-14 定，本节的总纲）

用户在 2026-09-14 连续做了**五次同样的动作**：

| 原字段 | 问题 | 改成 |
| --- | --- | --- |
| 攻击力 | 汇总值（"你有多强"）—— **已经算完的结论** | **六项属性**（维度） |
| **HP** | 汇总值（"你还剩多少"） | **伤势**（"你哪伤了"） |
| 幸运 | **掷骰系统的残留** | **删除** |
| 技能 | 汇总值（"你多擅长"） | **拆成事实，见下** |
| **法力值（MP）** | 汇总值（"你还能放几个"） | **「累」** —— 写在角色的「当下」段里（手抖、耳鸣、脸色发白），不是一个新的数字 |

> ⭐ **第五次是最后来的，也是最漂亮的一次。**
>
> 改成中魔之后需要"施法的代价"，而最顺手的写法就是加一个**法力值** ——
> 那正好是"**存一个已经算完的结论**"。
>
> 用户给的写法是**一句台词**：
>
> > *「很累的，你懂不懂魔法啊？放十个火球术你想让我直接榨干吗？」*
>
> **代价于是变成了角色的状态，而不是角色的面板。**
> 它落在已有的「当下」段里（手抖、耳鸣、靠墙喘）—— **一个新字段都不用加。**

> ⭐ **总原则：状态里存事实，不存结论。**
>
> 「引擎只**存**事实、不**算**事实」—— 这条管着引擎的职责，也管着**状态字段本身**：
> **能算出来的，就别存。**
>
> 结论每轮**由判定 agent 现算**；状态里只留算它所需要的**事实**。

#### HP → 伤势

```js
伤势: ["左臂骨折", "肋下刀伤（未愈）", "轻度脑震荡"]
```

- **死亡不再由血条归零触发** —— 判定 agent 判"这一击够不够致命"。
  对"媒介优先"来说这是好事：**死亡不该是"血条空了"这种机械事件**
- **愈合**：时间推进后由角色 agent 判定哪些伤好了、从列表里删掉
- ⚠️ **只记"会影响后续判断的伤"**（重伤、残废、中毒、诅咒）；
  小擦伤留在故事里就行 —— 否则这个列表会无限膨胀

#### 技能：拆成"事实"，不拆成数字

用户原话：*「还有技能……啥是技能啊？」* —— **这个问题问得对，技能要分开看：**

| 它其实在说 | 性质 | 处置 |
| --- | --- | --- |
| "你**有多擅长**剑术"（剑术 45/100） | **汇总值** | ❌ 砍。而且**技能是"等级"的复数形式** —— 砍掉一个进度条却留下二十个，自相矛盾 |
| "你**会**火焰箭 / 会开锁 / 跟老猎户学过追踪" | **具体事实** | ✅ 留，但**不设数值字段** |

**"会什么"写在主控自己的角色条目里** —— 跟 NPC 一样。
（这正是第六节「主控走与 NPC 同一套状态机制」那句的兑现。）

于是"学技能"这个玩法变成：**在世界里获得一个新事实**
（"你在公会跟老猎人学了三天追踪" → 主控条目里多一条），而不是"技能点 +1"。

#### 钱：存硬币，不存"金钱"

> 用户原话：*「别存金钱，就存银币金币吧，如果玩家找到一个宝石，
> 那他就得找地方换成铜币，不然花不出去**还会被人偷**。」*

| | 抽象金钱（一个数字） | 具体的硬币与物件 |
| --- | --- | --- |
| 能被偷吗 | ❌ 数字没有实体，被偷像在扣分 | ✅ **当然能** —— 它就是揣在你怀里的东西 |
| 宝石怎么处理 | 自动折算成钱 | ✅ **它是物品，不是钱** —— 花不出去，得找商人兑换 |
| 重量 / 磨损 / 成色 | 都没有 | 都有 |

**所以：**

- 硬币就是**背包里的物品**（「金币 ×3」「银币 ×12」）—— 面额档位待用户最终确认
- **宝石、首饰、欠条和硬币一样，都只是背包里的物品** —— 没有"钱包"这个独立概念
- 这是同一条原则的**第五次**应用：**存世界里数得出来的具体东西**

> ⚠️ **一条待定的实现问题**：硬币的**加减法谁做**？
> 模型做符合"引擎不做判断"，但模型算术不可靠；引擎做又要加第二个工具（破了"只有一个工具"）。
> **AI 建议：先让模型做，主 agent 在校验层兜底；真发现总算错再加工具**（符合"不提前预留"）。

#### 角色条目的四段结构（2026-09-14 定）

**每个角色 —— 主控和 NPC 一视同仁 —— 的条目天然分四段，按「寿命」排：**

| 段 | 是什么 | 例子 | 变化频率 | 镜头离开后 |
| --- | --- | --- | --- | --- |
| **固有** | 这个人本身 | 六项属性 · 本事 | 很少变 | ✅ 留 |
| **关系** | 她与别人的连接 | 和主控：队友（经历：在酒馆认识的…） | 有变动才改 | ✅ 留 |
| **携带** | 身上带着的东西 | 背包（武器 / 防具 / 硬币 / 杂物） | 有变动才改 | ✅ 留 |
| **当下** | 这一秒的样子 | **穿着 · 伤势 · 姿势 · 心情** | **当前场景里每回合更新** | ❌ **丢** |

> 💡 **这个四分和「NPC 三级分辨率」是同一件事的两面**：
> 分辨率说的是「**离得越远，知道得越少**」，四段说的是「**分的是哪几类信息**」。
> 镜头离开后只有「当下」可以丢；前三段必须留着 ——
> 否则队友再见面时，他包里的东西、和你的交情，全没了。

> 📌 **「伤势」归在「当下」** —— 它和穿着、姿势、心情是一家（"此刻的样子"），
> 而不是和背包一家（"拥有什么"）。

#### ⭐⭐ 类型定位：这张卡是「美少女游戏」（2026-09-14 用户拍板）

用户原话：*「基调：冒险者地牢、成长、一点点悬赏的功利心。**女人，女人，女人！**
呃我没有这么饥渴，我说实话，只是你得体现一下美少女游戏的特征。」*

**这不是"加点女性角色"，是给卡定类型。** 差别在于：

| | 冒险小说 | 美少女游戏 |
| --- | --- | --- |
| 世界 | **是内容** | **是背景** |
| 人物 | 是背景 | **是内容** |
| 地牢 / 悬赏 / 公主 | 目的 | **让人跟人待在一起的理由** |

⭐ **说「这是美少女游戏」五个字，比写十条「要多描写女性」有用。**
这是「**点名框架**」手法的**第四次**应用 —— 前三次是 Bartle 玩家类型、自我决定论、大五人格。
套路没变：**一个专有名词，省掉十行解释**，而且借来的是模型读过的**整个类型传统**。

**落到实处的是这几条**（都写进卡的 `【女人】` 和 `叙事风格` 了）：

| 原则 | 卡里的原话 |
| --- | --- |
| 先写人再写景 | 「先把屋子描述三百字、最后才提一句『柜台后站着个女人』，是把这张卡最好玩的部分浪费掉」 |
| 每个人都有说话方式 | 口头禅 / 句长 / **怎么称呼你** / 什么时候闭嘴 ——「写不出说话方式的角色是立牌，不是人」 |
| 日常要有分量 | 「下地牢之前先在镇上待一会儿；回来之后卖东西、养伤、喝酒，这三场都是戏，不是过场」 |
| 不是人人都喜欢你 | 「有人嫌你穷、有人嫌你麻烦、有人已经有人了。别把这张卡写成『谁见了你都脸红』」 |

> ⚠️ **「为什么镇上女人多」不解释。** 卡里只给一句世界观顺口溜
> （男人伐木的伐木、当兵的当兵、下地牢的没回来，铺子公会药房旅店都是女人在管事），
> 然后明确写：**「镇民不觉得这有什么奇怪，你也不该 —— 别解释，别找补，别让旁白点评这件事。」**
>
> 理由：这是**类型惯例**，不是需要世界观的设定。硬找补只会让模型每一场戏都惦记着解释它，
> 那才是真的出戏。**用一句玩笑话把它按住，比造一套社会史划算。**

> 📌 **开局必须立住这个基调。** 开场文本是模型的**行为模板**（见 `.agents/skills/verification`「示例是模型的行为模板」），
> 所以《晨风镇》的开局改成了：老板娘出场（外貌两笔 + 一句揶揄 + 一个旧烫疤），
> 跟他说话是「……收钱的」，转头对后厨的人「语气比刚才对你软得多」。
> 一句话交代了三件事：**她有自己的事、她对你不算热情、这个镇上的女人不是为你存在的。**

#### ⭐ 固有段里的三样：能力 / 生平 / 性格（2026-09-14 补）

用户原话：*「每个角色都加一个**人物生平**，一两句话，再加一个**性格**，
可以用**大五人格**模型，比如高宜人性低神经质这种的。」*

| 字段 | 写什么 | 变不变 |
| --- | --- | --- |
| **本事** | 会什么（「跟老猎户学过追踪」） | 很少变 |
| **生平** | 一两句话 —— **她来这儿之前**是什么人 | **不变**（那是过去） |
| **性格** | **大五人格**（OCEAN）+ 一句人话 | 很少变 |

> ⭐ **「生平」和「关系」的分工**（这条分清楚，两个字段才不会打架）：
>
> | 字段 | 管哪一段 |
> | --- | --- |
> | **生平** | **她是从哪儿来的** —— 你认识她**之前**的事（不变） |
> | **关系** | **她跟你之间发生了什么** —— 认识你**之后**的事（会变） |

**为什么是大五，不是 MBTI**：大五是**人格心理学里实证支持最扎实的模型**；
MBTI 在学术上信效度一直被诟病。
**点名一个框架 = 借用模型读过的相关文献** —— 所以要点一个「模型读过很多、而且它是对的」的名字。

> 💡 **这是「点名框架」这个手法的第三次应用**（前两次都在精神分析：**Bartle 玩家类型** + **自我决定论**）。
> 三次都是同一个套路：**一个学术名词，省掉十行解释。**

> 📌 **但主控不预设性格。** 玩家在世界里的那个身体是什么样的人，该由**玩家自己玩出来** ——
> 卡里只写了「他是个能代入的普通人」。给主控预设大五，等于替玩家决定他是谁。

#### ⭐ 角色的两层：次要 / 主要（2026-09-14 用户从旧项目带来）

> 用户原话：*「哪怕是**王公贵族**这种客观上很重要的人，
> 如果只是玩家在街头擦肩而过，那就**没有仔细生成的必要**。」*

**核心那句话：**

> ⭐ **「重要」是相对于玩家的，不是相对于世界的。**

| 层 | 长什么样 | 什么时候用 |
| --- | --- | --- |
| **次要** | **一行就够** —— 「街角卖烤栗子的老头」，**没有名字、没有属性** | 背景、路人、擦肩而过的人 |
| **主要** | **完整四段**（固有 / 关系 / 携带 / 当下） | 玩家会再见到的人 |

**升级的判据**（用户 2026-09-14 **二次修正**）：

> *「主要角色的标志应该是**玩家展现出和 ta 建立关系的意愿**，在精神分析那块评估。
> 哪怕玩家**每天都找同一个商人进货，也不能说明啥**呀。」*

⚠️ **AI 的第一版写错了**：它用的是**行为频率**（“反复出现”“实质互动”）——
用户一句反例就推翻了：**功能性重复 ≠ 意愿**。

| | 判据 | 谁判 |
| --- | --- | --- |
| ✅ **正确** | **玩家有没有表现出想跟这个人建立关系的意愿** | **精神分析** —— 全流程只有它读得到玩家 |
| ❌ 错误（AI 初版） | 他出现过几次 / 跟玩家说过几句话 | —— |

**判和做分开**（跟「判定 vs 叙事」是同一个模式）：

```text
精神分析（读玩家 → 输出「关系意向」名单）
    ↓
角色环节（照着名单升级：补全四段 + 给他一个名字）
```

**什么算「意愿」**：有没有问对方的名字 / 有没有多聊两句 / 有没有给对方带东西 / 还记不记得上次说过的话。

> ⚠️ **大纲环节不能点名升级** —— 那会让「玩家不感兴趣的人」变成主要角色，违背这条判据。
> （AI 初版给了它这个权力，已删除。）

> 💡 **这条跟两个已有的东西咬合得很紧：**
>
> **① 它是「存在性判断」（决定 #10）之外的第二根轴** ——
>
> | 维度 | 决定什么 | 机制 |
> | --- | --- | --- |
> | 在不在场 | **调不调用**他 | 三级分辨率（区域 / 地点 / 场景） |
> | **重不重要** | **记不记得细** | **这一层（次要 / 主要）** |
>
> **② 它给「有名字的就不会死」补了另一半** ——
> 次要角色是背景，不会被卷进致命的事；**一旦要被卷进去，他就该升级了。**
> 于是"名字"同时是**记得细的标志**和**免死金牌** —— 两件事用的是同一个开关。

#### ⭐「关系」：自然语言，不是数字（2026-09-14 定）

用户原话：*「倾向于不要有好感度数字，不然又要写规则」* ——
这条直接落在「**状态里存事实，不存结论**」上。

```json
"关系": [
  { "对象": "主控", "是什么": "队友",
    "经历": "在酒馆认识的。觉得他不靠谱，但一个人很难下地牢，勉为其难答应了组队。" }
]
```

| 字段 | 写什么 |
| --- | --- |
| `对象` | 对方的名字（主控的名字开局就定，**直接写名字，不用占位符**） |
| `是什么` | **一个短标签**：队友 / 债主 / 点头之交 / 仇人 / 雇主 |
| `经历` | **自然语言**：为什么是这个关系 |

> ⚠️ **`是什么` 不许写成数字** —— `"好感": 80` 是错的。
> 它跟「没有等级」是同一条线：**好感度也是一个"已经算完的汇总值"**，
> 跟攻击力、HP、等级同一族。玩家该像判断"我打不打得过巨魔"一样，
> **通过故事判断"她喜不喜欢我"**。
>
> 每个角色条目都有这一段（主控也有），两边描述的是同一件事，
> **同一次输出里一起写** —— 跟「背包转移要成对出现」是一个道理。

##### ⭐ 那关系怎么"推进"？—— 靠**称呼**（2026-09-14 补）

「不要好感度」很容易滑向另一个坑：**那玩家怎么知道自己推进了没有？**

答案是不用造新字段 —— 用**称呼**：

> 从「喂」→「你」→ 叫你的名字 → 给你起个绰号。

这个变化本身就是剧情，而且它**天然就是事实**（她嘴上怎么叫的，白纸黑字）。
她第一次不叫「先生」而改叫「你」的那一下，比一场打斗值得写。

配套的两条（都写进卡的 `【女人】` 里了）：

| 写什么 | 例子 |
| --- | --- |
| **她主动做了什么** | 主动搭话 / 给你留了好位置 / 少收你钱 / 问你下次什么时候来 |
| **她记得什么** | 你上次说过的话、你欠她的、她答应过你的 |

> ⭐ **这三样一起，正好替代一整条好感度进度条** —— 而且全是事实，写不写都不会自相矛盾。
> 数字进度条要模型"算"，事实进度条只要模型"记得"。

#### 示例卡的状态字段（汇总，2026-09-14）

```js
主控 · 固有：  六项属性（力量 敏捷 技巧 魔法 智力 魅力）· 本事（会什么）
主控 · 当下：  穿着 · 伤势 · 姿势 · 心情        ← 不是 HP

```

## 八、已知风险

### 风险 1：作者把图写坏（已降级 —— 流程固定后不再有"演化失控"）

**调用次数在做卡时就确定了**，所以"演化停不下来"这类风险**不存在**。
剩下的是**作者手滑**：

```
① 图里写出环：A → B → A → … 永不结束
② 单节点次数过大：作者写「重复 10 次」× 每次 5 个 agent = 一轮 50 次调用
```

对策：**静态校验**（发卡前检查有没有环）+ **单轮调用硬顶**（兜住手滑）。
这不是优化，是防止**一张坏卡把玩家的额度烧光**。

> 🆕 **2026-09-14**：示例卡是**纯线性图**（无循环、无扇出），所以上面 ② 当前不适用 ——
> 这条留着防将来作者真用上循环。**① 仍然有效**（手写 JSON 很容易写出环）。

### 风险 2：成本随 agent 数量线性增长

```
5 个 subagent × 3000 token 上下文 = 每轮 15000 token 输入
（对比：现在单 agent 约 6000）
```

**真正的 token 大头不是"多几次调用"，而是"上下文被复制了几份"。**
决定 #11 选了"全敞开"，代价就是这个 —— 用成本换准确性，**用户已明确接受**。

### 风险 3：多 agent 的一致性

同一事件被两个 agent 各自判断 → 出现两个版本（如都算伤害，一个说 12 一个说 8）。
→ 防线已定（洞察 4：中途只写工作副本、提交是唯一入口、主 agent 合并），
但**合并规则未定**（待定 5）。

### 风险 4：作者写不好图，游戏就不好玩

决定 #9 把"节奏"交给了作者的图设计质量。这是**有意的**（目标 ②），
但意味着**预设卡模板的质量直接决定新手体验** —— 不能只做机制、不做示范。

## 九、踩过的坑（别再犯）

| 坑 | 后果 | 教训 |
| --- | --- | --- |
| **单模型一轮里扮演多个引擎**（旧项目的"人格分裂技术"） | 引擎一多，超出单轮输出能力：质量崩、格式飘 | **职责分离要靠独立调用，不是靠提示词里排队** |
| 把规则写进引擎 | 玩家只会用"引擎认识的动词"，自由度死掉 | 规则交给 AI 判断 |
| 把"引擎持有事实"理解成"引擎计算一切" | 引擎越来越重，越来越像传统游戏 | 引擎只**存**事实，不**算**事实 |
| **把叙事性判断写成引擎规则**（如"关键时刻检测器"） | 又变成 `if HP<30` 那套，且规则永远不够用 | 叙事判断交给提示词（决定 #14） |
| **概念改了但文档别处没跟着改**（本次修复的起因） | 同一文档里"关键时刻"有两个矛盾含义，下次读的人必错 | 改决定后要**全文扫描**旧概念残留 |
