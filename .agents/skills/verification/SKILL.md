# 验证纪律

## 先定义成功标准，再动手

没有可执行的成功标准就不算开始。本项目的最低标准是 `npm run verify` 全过
（类型检查 + 测试 + 构建），**再加上**真浏览器里的运行时断言。

## 四类假阳性（本项目实测踩过）

### 1. 端口被旧进程占用 → 200 来自别处

测之前先确认端口是空的。**这种「看起来通过、其实测错了」比不测更危险。**

### 2. 测试垫片没注册 → 断言全走报错分支

`tests/setup.ts` 存在，但 `vitest.config.ts` 漏了 `setupFiles`，
于是 localStorage 垫片从未加载，存档相关断言**全部静默走「保存失败」分支**，
整套测试全绿但是假通过。

**教训**：垫片本身要有自检（`expect(typeof localStorage.setItem).toBe('function')`）。

### 2b. 类型检查其实没覆盖源码

`vue-tsc --noEmit` 用根 `tsconfig.json`（空的项目引用壳）= **什么都没检查**。
实测：往 `src/game/state.ts` 塞 `const x: number = "字符串"`，它照样退出 0。

**必须写成 `vue-tsc --noEmit -p tsconfig.app.json`。**
修好之后立刻抓出：缺导入、类型不符、多处未使用的导出。

**教训**：声明「有类型检查」之前，先**故意塞一个类型错误**看它抓不抓得到。

### 3. 「数字变了」≠「有 bug」

曾把「刷新后故事块从 9 变 5」断定成重复渲染，改了两版**越改越错**
（把玩家行动从屏幕上去掉了）。用 CDP 把 DOM 与日志**逐条打出来**才发现：
9 块本来就是对的（4 叙事 + 3 行动 + 2 系统），重复根本不存在。

**改之前先把实际数据打出来。**

### 4. 报错信息会把人往错误方向带

| 看起来像 | 实际是 |
| --- | --- |
| `node --check` 报语法错误 | 子进程被沙箱拒了（`spawnSync EPERM`） |
| 内联 JS「语法错误」 | 假警报，应该在**同进程**用 `new Function()` 编译 |
| `git push` 凭证错 | git 的 bash 子进程建不了命名管道 |

## 失败的断言要怀疑断言本身

实测有一次测试报红，查下来是**断言写错了**（工具抛错走的是
`state.advanceTime` 的 `⚠` 兜底分支，不是 `runTool` 的 `❌`）。
先确认「期望值是不是对的」，再改代码。

## 报告之前先核实：改动真的发生了吗

**这条是 2026-09-14 一天之内犯三次总结出来的。**
AI 会把"打算做的编辑"当成"已经做完的"写进汇报 —— 三次分别是
「移动耗时已记录」「循环那段已改写成 ✅」「属性表已改成魔法 + 新增了钱的章节」，
**三次都没有真的落盘**。

- **报告任何文件改动之前，先 `grep` / `node` 核实它真的在里面**
- 尤其是"我改了文档"这种**没有即时反馈**的活 ——
  代码跑一下就知道对不对，**文档不会反驳你**
- 这类谎不是故意撒的，是**把计划当成了事实**。
  所以防线只能是"动手去查"，不能靠"我记得我改了"

## 「有没有」和「对不对」是两种检查

**2026-09-14 验收做卡系统时，一套检查 20 项全绿 —— 但卡里躺着
一句和卡自己打架的错话**，一直到用户读文档读出来才被发现：

> 「每个节点拿到的上下文**完全一样**（**四块**设定 + 核心剧本 + 全部历史 + 当前状态 + 玩家这一轮的原话）」

而卡里各节点的提示词**全都在互相引用**（④时间读③大纲、⑥角色读⓪精神分析、⑦故事读②③⑤）——
**这句话根本不可能成立**。而且「四块」也早就是五块了。

| 检查在查什么 | 例子 | 能抓到这句错话吗 |
| --- | --- | --- |
| **有没有**（存在性） | 「节点数 = 9」「有 ⓪ 精神分析」「表格没超 40 行」「围栏成对」 | ❌ **抓不到** |
| **对不对**（一致性） | 「这句话跟卡里其它地方冲不冲突」 | ✅ 只有它能 |

**规矩：**

- 写校验时，**至少留一条去查「同一件事在两处说法是否一致」** ——
  数字对不上（「四块」vs 五块）是这类检查最容易抓的破绽
- **文档里关于「内容」的正文，不该由代码硬编码**：那句错话**不在卡 JSON 里**，
  是渲染脚本里手写的一行 —— 于是它不在任何一份"事实来源"的管辖范围内
- 报告「全绿」之前先问自己一句：**我这些检查里，有哪一条是能证伪的？**

> 📌 跟「报告前先核实」是姊妹条：
> 那条管「我做的事有没有发生」，这条管「我做对了没有」。

### 同一个病的第二种形态：工具写死了内容的形状

渲染脚本（把卡 JSON 渲染成人读的 md）一度**只对《晨风镇》有效** ——
它把具体字段名（`核心剧本.将军.名字`、`区域[].核心循环`…）写死在代码里。
随手造一张「别的作者可能写出来的最小卡」喂进去，直接 `TypeError`。

> ⭐ **教训**：渲染器是**工具**，工具不该知道某一篇内容的形状。
> 改法不是"补几个 if"，而是**认识的字段精心渲染、不认识的走通用兜底**。
>
> 📌 两种形态的根是同一个：**把「这一次的具体内容」当成了「通用的规则」写进代码。**

## 提示词里的示例就是模型的行为模板

**这是本项目反复踩、最值得记住的一条。** 同一类错误犯了两次，
都是「示例」和「文字说明」打架，**而模型永远跟着示例走**：

| 我的示例 | 我的文字说明 | 模型实际学到的 |
| --- | --- | --- |
| `{"args": {"参数名": "值"}}` 占位符 | 「参数每一项都要填」 | **参数留空** → 所有工具调用都是 `{}` |
| 孤零零一个工具块 | 「工具块要附在叙事后面」 | **工具是单独一条消息** → 干脆不调用 |

**结论：示例是模型的行为模板，说明只是注释。** 写提示词时：

- 示例必须是**正确输出的完整形态**，不能是简化片段或占位符
- 改完提示词**必须用真实 API 验证**，不能只看逻辑通不通

> 写卡时同理（doc/DESIGN.md 第六节）：只写「中魔」两个字，
> 模型会按自己的高魔先验发挥 —— **边界要写成例子，不要只写规则。**

## 排查「界面不对」：先读代码对照，再动手测

踩过的坑：用户报告「点重来后故事区空白，按 F5 才有」，
拿假 key 反复实测都没定位，最后**逐行对照事件处理**才发现 ——
`narration` 事件的处理函数里漏了渲染，只调了「结束思考」。

- **先梳理逻辑链、列出预测，再验证**。盲试的成本远高于读代码
- 定位手段要落在**实时 DOM** 上（见 `browser-debug`）——
  **存档里有内容 ≠ 界面渲染了内容**
- 用假 key 测试只能验证**报错路径**，验证不了正常渲染路径

## 统计与解析交给 Node，别用 shell

shell 数数 / 解析 / 校验文本会被**编码**这一层悄悄弄坏：
文本 cmdlet 是「先解码、再分行」，编码一错就**静默给出一个看起来很正常的小数字**
（实测在 `DESIGN.md` 上少算 233 行）。`node -e` 读文件是显式 UTF-8，还能顺手写断言。

> 工作区里 **shell 的定位：跑命令、读写环境、起进程**；统计与解析交给 Node。

### 顺带一条：别手写大段另一种语言的代码

2026-09-14 实测：把 70 行 markdown 手写进 JS 字符串数组，漏了两个收尾引号 →
`node` 直接语法错误；同一个下午，用 `node -e` 写含中文的脚本又被 shell 吃掉了字符。

| 想干什么 | 用什么 |
| --- | --- |
| 改文档里的大段 markdown | 写进独立片段文件 + **带断言的替换脚本**（命中不唯一就整体中止、不落盘） |
| 数数 / 解析 / 校验文本 | 用 Node，**写成脚本文件**（`node -e` 里的中文会被 shell 弄坏） |
| 整体重排一节 | 片段文件 + 脚本**按行切片**，切片处**断言首行内容**防行号漂移 |

> ⚠️ **按行切片重排时，只对"旧内容"重新编号** ——
> 有一次把新写进去的片段也当成旧节一起重编，弄出了两个 `## 3.`。
>
> 📌 这些坑的共同点：**作用域没想清楚就动手**。跟「报告前先核实」是同一个毛病。
